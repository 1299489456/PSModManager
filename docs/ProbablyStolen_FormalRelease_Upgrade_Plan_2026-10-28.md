# PSModManager 正式版升级分析与功能改进方案

日期：2026-10-28（America/Los_Angeles）

对象：Steam AppID **4348910**，本机 Build **26284217**，界面版本 **VERSION 100-Rev3**，内部兼容版本 **0.46D**。

状态：**功能与方案评审稿**；分析已完成，产品升级尚未实施，功能清单尚未逐项确认。

新版面向 Probably Stolen 正式版的原生 Mod 体系，移除 MelonLoader，以 Steam 创意工坊替换 Nexus，并围绕完整模组包、依赖关系和启用顺序重整管理方式。本文整合游戏机制分析、真实工坊包结果、32 项功能评审清单、界面与数据设计、迁移方案、实施顺序和验收条件，供产品范围评审与后续开发使用。

**阅读导航：** 功能取舍见 §1.2；底层机制与真实样本见 §2—§6；架构、布局和工坊接入见 §7—§10；实施与验收见 §11；待确认事项见 §12；源码和资料定位见 §13。

## 1. 结论：只面向正式版原生模组，以 Steam 创意工坊为在线来源

**推荐把 PSModManager 升级为“原生模组、工坊订阅、配置方案与安全恢复”的外部管理工作台。** 游戏负责执行模组和批准权限，Steam 负责订阅内容的下载更新，管理器负责跨来源盘点、预检、方案、恢复和诊断。

这次变化影响的是整个管理模型，而不只是把 `IL2CPP` 标签换成 `Mono`：

- 原生加载器读取 `manifest.xml`、显式 DLL 清单和 `IMod` 入口；旧版裸 DLL/MelonMod 导入规则不能原样沿用。
- 启用状态和顺序在游戏用户数据中，不在 DLL 的存在与否上。**停用原生模组不应删除文件，停用工坊模组更不能修改订阅目录。**
- 原生游戏有权限扫描、逐机批准、更新重新评估、签名信任列表；不能用“已安装”代替“获准加载”。
- 内置自动排序已经存在，但当前实现不能保证 DLL 初始化、Harmony 打补丁、Hook 订阅的实际顺序。
- 存档、原生配置、模组自定义文件和工坊下载属于不同生命周期，必须分别管理。

正式版写操作应在 P1 原生状态适配及真实读回验证完成后启用；P0 先提供只读盘点并隔离旧写入入口。

### 1.1 已确定方向与推荐接入方式

- **移除 MelonLoader 支持，而不是隐藏入口或继续维护双适配器。** 新版只管理正式版原生 Mod；不再安装、修复、升级或启动旧 IL2CPP/MelonLoader 环境。
- **Steam 创意工坊替换 Nexus。** 移除 Nexus 页面、账号/API Key、下载及 `nxm://` 接入；保留本地原生目录/ZIP 导入。已下载的合法原生包不因来源曾为 Nexus 而被删除。
- **布局与管理方式必须适应依赖和排序。** 推荐借鉴 RimCrow 的“可用列表 → 启用与顺序 → 保存运行”，按完整 Mod 包而非 DLL 管理；具体三栏布局见 §8，仍属于待评审设计。环世界的清单、核心包和排序规则不能直接套用。
- **用户提出使用账号授权或匿名方式获取工坊 Mod。** 推荐默认通过已登录的 Steam 客户端完成账号订阅；匿名通道只在该游戏/条目允许时下载公开内容，不产生用户账号的订阅记录。本机 AppID `4348910` 的匿名下载尚未实测，应用内直接授权也需验证接入条件，见 §9。

新版不保留旧加载器与 Nexus 的并行产品路径。旧包和方案提供迁移预览，旧运行环境不再是兼容目标；历史记录和用户文件仍需保留。

## 3. 正式版原生加载机制及管理影响

### 3.1 原生包契约：以整个目录为安装单元

典型布局：

```text
Mods/<包目录>/
  manifest.xml
  MainMod.dll
  Assemblies/             # 可选依赖 DLL；仍必须在清单中逐项声明
  preview.png             # 本地预览可选，工坊远端封面独立
  Textures/
    Items/
    Paper/
  Sounds/
  Localization/
  LootTables/
  Books/
  <模组自行定义的其他资源与说明>
```

当前解析器读取以下字段：

| 字段 | 本机代码的实际含义 | 管理器处理 |
|---|---|---|
| `ID` | 非空，最多 64 字符；字母、数字、`_-.`；不能以 `.` 开头 | 用作游戏逻辑身份，保留大小写；额外检查 Windows 路径碰撞 |
| `Name/Author/ModVersion/Description` | 展示元数据；版本是字符串 | 原文保留；不要自行强制转换为 SemVer |
| `GameVersions/Version` | 游戏 UI 兼容提示 | 原始版本与解释后的兼容提示同时保留 |
| `Prerequisites/Mod` | 其他模组的 ID 列表 | 有向依赖图，不是 NuGet 版本约束或 Steam 自动订阅清单 |
| `Assemblies/Assembly` | 必须存在且非空；列出要加载的 DLL | 相对路径、存在性、越界、重复、入口与依赖库角色检查 |
| `Capabilities`（含 `Capability` 子项） | 父元素必须存在；子项可空；值必须是游戏识别的能力 | 展示声明权限，并与扫描/批准/本次执行证据分开 |

关键细节：

- **XML 根元素名称当前未被限定。** 真实样本同时出现 `<Manifest>` 与 `<Mod>`，游戏都接受；不能把某个社区工具的严格判断当作游戏标准。
- 本地发现扫描 `Mods` 的直接子目录；不能把裸 DLL 直接丢到根 `Mods` 就期待原生发现。
- `Assemblies` 中未声明的 DLL 不参与正常加载；根目录和 `Assemblies` 目录里的未列 DLL 会影响启用检查。其他目录中的文件也不能被导入器随意忽略。
- 发现阶段的 `IMod` 检查只是 DLL 字节初筛；真正加载时才检查类型。外部管理器应做 PE/CLI 元数据检查，不能把字符串命中当作入口已验证。
- 一个 DLL 有多个 `IMod` 时游戏只选第一个；多 DLL 包可能产生多个入口记录。管理器应报告这种结构，而不是把一个依赖 DLL 误列成独立模组。
- 原生包复制必须保留完整相对目录，不能只抽取 DLL，更不能把所有依赖展平到 `UserLibs`。

证据：E02、E03。

### 3.2 生命周期：先执行 DLL，后应用保存顺序

当前 `ModLoader.Awake()` 的实际链路：

```text
收集游戏/框架程序集名 → 读取批准和信任列表 → 读取 modOrder
  → 扫描本地目录并按需加载 DLL
  → 扫描工坊目录并按需加载 DLL
  → ApplySavedOrder
  → ValidatePrerequisites（警告）
  → 贴图 / 本地化 / LootTables / Books / 异步音频
  → 启动审计日志 → 后台刷新信任列表
```

加载一个入口 DLL 时：`Assembly.LoadFrom → 创建 IMod → Harmony.PatchAll → Init(manifest) → OnEnable`。

**保存顺序在这些动作之后才应用。** 因此：

- 排序会影响后续遍历和资源加载，不能据此保证 `Init`、Harmony 或 Hook 订阅已按依赖先后执行。
- 缺少 `Prerequisites` 当前只记录警告，不能当成原生加载前的强制依赖阻断。
- UI 的自动排序是对当前激活项做依赖 DFS；缺失依赖不自动安装，循环依赖也不会给出完整循环诊断。
- Hook 的执行按委托订阅列表进行，不会在触发时重新依据 `modOrder` 排序。

**改进选择：** 提供可解释的依赖排序和缺失/循环检查，但把输出称为“保存顺序”；明确提示当前 Build 的初始化顺序限制。依赖必须先初始化的组合应列为风险/阻断项，不能用改文件夹名或补丁劫持加载器来承诺可靠性。将此代码链与最小复现交给游戏开发者修复，外部管理器不默认修改游戏程序集。

此外，`OnEnable` 出错时游戏尝试移除该 Harmony 实例的补丁，不能回滚模组已经写出的文件或业务变更；普通菜单停用只修改下次启动状态，`OnDisable` 主要在退出时调用。**“停用”不是热卸载。**

证据：E02、E04。

### 3.2.1 依赖图要区分“需要安装”与“需要排在前面”

目前七个样本未声明 `Prerequisites`，但游戏已经支持该字段。不能只按这七包的空依赖实现一套没有依赖模型的管理器。

| 关系来源 | 身份与用途 | 处理方式 |
|---|---|---|
| 原生 `Prerequisites/Mod` | 原生 Mod ID；作者声明的必需模组 | 计算启用闭包和反向依赖；缺失/未启用时阻止应用该方案；以依赖在前生成保存顺序 |
| Steam 必需工坊项 | Workshop Item ID；获取与订阅关系 | 获取后解析清单，建立 Item ID → Mod ID 映射；不能拿工坊 ID 当原生 ID |
| Steam 合集成员 | 一组工坊条目 | 仅用于批量选择，不自动变成成员之间的依赖或加载次序 |
| 管理器自定义前后规则 | “A 在 B 之前/之后”，带规则来源 | 保存于管理器方案，不擅自给游戏 manifest 增加 `loadBefore/loadAfter` 字段 |
| 程序集/补丁/资源分析 | 引用、同名库、补丁交集等线索 | 用于预检和解释；不能仅凭同一补丁目标就生成硬性互斥或排序规则 |

Steam 的条目 children 可能来自依赖，也可能来自合集；必须结合条目类型解释。无法把缺失原生 ID 唯一映射到工坊条目时，提供搜索与用户选择，再核验下载包的 ID，不按相似名称自动订阅。[Valve ISteamUGC](https://partner.steamgames.com/doc/api/ISteamUGC)

### 3.2.2 自动排序应稳定、可解释、可撤销

- 自动排序使用稳定拓扑排序；无约束的项目尽量保持当前相对顺序，不把名称排序当加载排序。
- 输出每次移动的原因，例如“B 依赖 A，因此 A 移到 B 前”。预览后应用到工作草稿，并支持撤销。
- 必需依赖缺失、循环依赖或已选择的硬性规则冲突时，不提交半成品；显示具体路径，如 `A → B → C → A`。
- 用户前后规则与原生必需依赖冲突时，建议移除冲突的自定义规则，不静默忽略任一条。
- 拖动与快捷键调整后立即检查约束；有冲突仍可保留草稿，但不能“应用到游戏/保存并运行”。“保存方案草稿”不代表它已可运行。
- 停用基础 Mod 时列出受影响的反向依赖，提供“同时停用这些模组”或取消；不留下隐式失效的已启用子项。
- 缺失文件或下载中的目标保留占位及原因，不从用户方案中悄悄消失，也不能计为可加载。

这些操作改的是保存顺序。当前 Build 的初始化顺序限制仍按 §3.2 展示，不能借鉴 RimCrow 的界面后就假定两款游戏的执行语义一致。

### 3.3 来源优先级：本地同 ID 会遮蔽工坊

本地先扫描，工坊后扫描。同 ID 存在于两处时，本地副本获优先权；其他重复 ID 通常先发现者获胜，而不是“版本号最高者获胜”。

这会造成一种很实际的故障：玩家已在 Steam 更新模组，却一直运行旧的本地副本。

管理器应：

- 一个逻辑 Mod 下展示全部安装来源，清楚标注“实际使用：本地；工坊副本被遮蔽”。
- 将“切换为工坊版”作为显式操作，先备份、预检配置与存档风险，再移走本地包；不能静默合并目录。
- 来源变化后保留“待重新批准”状态，不能把旧来源批准复制到新来源。
- 区分停用、移除本地包、取消订阅；取消订阅成功也不意味着同 ID 本地副本已被删除。

证据：E03、E05。

### 3.4 三套版本号必须并存

本机同时存在：Steam Build `26284217`、菜单 `100-Rev3`、`Application.version` `0.46D`。模组清单里的 `0.46D` 不因此就是“旧 Demo 包”。

游戏 UI 只截取版本开头的数字和点，再做相等/点分段前缀匹配；不执行严格语义版本范围解析，也没有在 DLL 加载前强制阻止版本不匹配。

建议保存：`steamBuildId`、`displayVersion`、`applicationVersion`、`runtimeKind`、`nativeApiRevision`。兼容判断拆成“作者声明匹配、静态引用可解析、当前启动成功、实际玩法验证”，不把一个绿色版本号当成四项都通过。

其中 `nativeApiRevision` 是管理器对已识别原生 API/规则集的适配标识，不是本轮发现了游戏官方提供的独立 API 版本号；无法识别时应明确未知。

证据：E01、E04。

## 4. 权限与信任：尊重原生批准，同时补足解释和恢复

截图中的提示来自原生能力机制。当前能力包括：`files`、`network`、`process`、`dynamic-code`、`native`、`reflection-external`。

这些提示描述的是文件、网络、进程、运行时生成/加载代码、原生系统库和外部反射能力。**它们不是操作系统级沙箱。** 模组获准后与游戏在同一进程执行；“无声明权限”“扫描通过”“工坊来源”都不等于经过完整安全审计。

管理器至少应同时显示四组信息：

1. 清单声明了什么。
2. 当前版本扫描发现了什么，以及扫描规则对应的游戏 Build。
3. 此机器批准过什么，批准来源与版本是否仍相符。
4. 最近一次启动是否实际加载、被阻止或报错。

### 4.1 更新不是一律重新批准，也不是一律自动放行

原生机制记录清单与列出 DLL 的指纹。来源或 Workshop Item 变化会影响信任；执行指纹改变后会重新扫描，如果符合声明且没有扩大原已批准的检测能力，游戏可能自动刷新批准记录；新增能力、未声明能力、扫描拒绝等情形则不会继续照旧加载。

因此更新 UI 应显示“文件变化”“能力变化”“来源变化”“游戏当前判断”，不要把任何字节变化都说成权限升级，也不要承诺旧批准永远有效。

图片、音频等非清单 DLL 内容不都在原生执行指纹覆盖范围内。完整恢复快照仍应包含包内全部文件。哈希只用于必要的信任一致性、发布完整性或冲突判断，不作为每次刷新全库的默认操作。

还有两个容易被忽略的边界：相同指纹走快速放行，游戏版本变更本身不会使它重新扫描；远端新封禁撤销的是后续加载，并不会卸载当前进程已经执行的代码。管理器应显示“当前 Build 尚未重检”和“需退出当前会话”，而不是“已彻底隔离”。

### 4.2 管理器不能制造原生批准

- 第一次启用和需要重新审阅时，交给游戏原生 UI 进行确认；尚无有效批准时显示“待游戏批准”，已批准但未重启单列“待重启”。
- 不导入别人电脑的 `modTrust`，不随分享方案传播批准记录，不替用户开启 Developer Mode。
- 停用要保留原生“移出启用集合并撤销对应批准”的语义。恢复方案是恢复用户的目标选择，不是偷偷恢复已撤销的信任。
- 封禁、暂停或扫描拒绝应原样展示原因；不推荐通过修改信任缓存或使用旧记录绕过。

游戏还包含签名信任列表的缓存与更新路径。列表是可用的额外防护，但其缓存新旧、发行者查询延迟、当前进程已加载代码的不可卸载性都要留在状态模型中。具体算法、硬拒绝及恢复语义见证据 E06。

## 5. 配置、资源与存档：不能只管理 DLL

### 5.1 原生配置的文件不是完整配置 Schema

`ModConfig` 将值写入：

`%USERPROFILE%\AppData\LocalLow\Questing Goose Studio\Probably Stolen\ModConfigs\<ModID>.json`

格式是 `entries` 数组，单项为字符串 `key/value`。类型、范围、选项、中文标签、提示和 `requiresRestart` 在模组运行时通过 `Define` 注册，**不包含在该值文件中**。

首版应提供带备份的原始值编辑和已知配置的专用编辑器，明确哪些字段类型未知。不能根据 `"1"` 猜它一定是数字，或把未知值/未知字段清掉。

后续如确有需要，可做用户选择安装的原生小型辅助 Mod，只导出配置 Schema 和运行诊断；不让玩家基础操作依赖它，不接管批准，也不在外部进程执行 DLL 来“发现配置”。

离线修改后要重启/重新加载游戏才能可靠读入；修改文件本身不会自动触发 `OnModConfigApplied`。游戏运行中应阻止离线写入，避免它随后保存内存旧值覆盖用户更改。

证据：E07。

### 5.2 原生资源有精确路径、加载时机和冲突语义

- `Textures`、`Textures/Items`、`Textures/Paper`、`Sounds`、`Localization`、`LootTables`、`Books` 各有独立处理，不是任意递归扫描。
- 图片、音频、CSV、JSON 各自用对应读取器；应对大小、图片尺寸、格式和目录布局做预检。
- `Init/OnEnable` 发生在资源加载前；音频异步完成。`OnModAssetsLoaded` 是适合表示资源就绪的原生事件。
- 游戏导出 **44 个公开 Hook 事件**，覆盖物品注册、顾客生成、读档、营业/睡眠、提示、资源、配置、掉落表、纸面 UI 等。单个 Hook 处理器异常会记录来源并继续调用其他处理器，但不代表整个游戏逻辑可回滚。
- 掉落表操作采用操作日志顺序重放；同表的清空、添加、移除、调权重可能冲突。物品注册也可能替换已有 ID。相同 Harmony 目标只能提示“潜在交互”，不能直接断言互斥或自动排序可修复。

管理器可以静态显示资源目录错误、重复 ID、重复程序集、明显的同表操作和声明补丁触点；对于动态生成 ID、动态补丁和玩法相互影响，保留“需运行验证”，不要输出伪精确兼容分。

证据：E08、E09。

### 5.3 恢复应分层，不把全量回滚当成普通撤销

至少区分：

| 数据层 | 位置/内容 | 建议恢复单元 |
|---|---|---|
| 游戏全局状态 | `SaveFile.es3`：模组顺序/信任/工坊缓存与游戏选项共存 | 只改目标键；保留其他字段和 ES3 类型信息 |
| 原生配置 | `ModConfigs/<ID>.json` | 单个 Mod 配置，可预览差异 |
| 原生独立数据 | `ModData/<ID>/` | 按 Mod 保存，不自动清理 |
| 当前游玩数据 | `PlayerStore.modData`、物品 ID 等，随存档保存 | 完整槽位与相关索引，不做通用清洗 |
| 存档与历史 | `save_N.es3`、`save_N_day...es3`、`saves_index.es3` | 一致性快照，恢复前展示会替换哪些存档 |
| 自定义文件 | 例如游戏根 `UserData/CyberElectronics` | 按真实包规则单独纳入 |
| 工坊包内容 | Steam 管理的安装目录 | 不覆写在线订阅目录；本地快照恢复明确切换来源 |

本机 `SaveFile.es3` 确认是带 `__type/value` 的明文 JSON，`modTrust.value` 又是一层 JSON 字符串。**不能用只包含模组字段的新 JSON 替换整个文件**，否则会破坏游戏选项、键位等。对未知 ES3 编码/加密/结构必须只读拒写，而不是猜测转换。

游戏已有存档历史轮换。管理器不要另做一套看似等价、实则遗漏索引和旧日快照的复制方式。

存档中缺失物品工厂时，代码会创建 dummy 物品，再恢复部分已保存字段；这能帮助读档，但不恢复模组行为，容器结构也可能不同。故“仍能进入存档”不等于“卸载无损”。建议切换高风险内容包前做完整快照，并优先使用游戏自己的槽位副本进行后续验证。

证据：E10；本轮未在真实存档上测试卸载或恢复。

## 6. 真实七包带来的适配要求

以下版本和权限来自本机文件，不代表以后工坊更新后的状态。

| 工坊 ID | 模组 / 版本 | 声明能力 | 管理重点 |
|---|---|---|---|
| 3828868413 | Item Details / 物品详情 0.4.1 | 无 | 最近启动有实际运行证据；原生配置样本 |
| 3829050213 | Probably Stolen Workshop Uploader 0.4.1 | files, network, process, native | 社区上传器；不能等同游戏内置功能或官方发布标准 |
| 3829024993 | 小鼠养殖管家 0.2.0 | 无 | 玩法修改；停用不撤销已产生的存档变化 |
| 3829106910 | 店铺助手 / Shop Assist 1.1.0 | reflection-external | 反射依赖与正式版 API 变动诊断 |
| 3828949943 | 小窝特性扩展 / XIAOWO-TradePerks 2.0.1 | reflection-external | 玩法特性与持久化影响 |
| 3828902092 | 霓虹旧货：电子产品 + English Translation Patch 1.4.31 | files, dynamic-code, native, reflection-external | 14 DLL 多程序集包、壁纸资源、自定义数据路径、内容存档 |
| 3828909239 | Probably Multiplayer 2.0.2 | files, network, process, reflection-external | 联机协议和同版本组合必须单独验收 |

### 6.1 不能从“程序集名称能找到”推导出“游戏可用”

21 个 DLL 均有 CLR 元数据；静态 AssemblyRef 简名均可在同包或游戏 Managed 中找到。但还存在引用版本差异，运行时方法/字段解析、反射目标、Harmony 补丁匹配、联机协议与玩法联动仍需实际验证。

七包的 `Prerequisites` 都为空或未声明，不能据此断言它们没有隐式依赖。电子包中携带的库与其业务 DLL 应按程序集角色处理，不要因为看见 `System.*` 就自动删除，也不要仅比较 DLL 文件名就判定框架冲突。

实际还有 **7 包、8 个 IMod 入口** 的区别：电子扩展与英文翻译在同一个包内分别有入口。原生 `LoadModDll` 会逐入口创建 `LoadedMod`，包尾只对最后一条记录补充完整信任字段，UI 又逐条遍历。这是同 ID 多记录/部分字段差异的静态风险，需要重启后实测；管理器应按包汇总、按入口保留失败明细，不按日志条数推算成功包数。

### 6.2 上传器存在真实格式分歧

已反编译的社区上传器 `ProjectStore.ReadMod` 强制根元素为 `<Mod>`；其余六个实际工坊包使用 `<Manifest>`，而游戏解析器并无这个限制。

**结论：不能直接复用该上传器的验证逻辑作为 PSModManager 的标准包解析器。** 可以参考其暂存和发布流程，但包合法性应按游戏版本适配；不要为了过上传器检查，未经提示重写作者清单，这还会改变原生信任指纹。

### 6.3 文档路径也可能落后于实际实现

电子包壁纸说明仍提到游戏 `Mods` 路径，实际 DLL 以自身程序集位置查找 `CyberElectronics/Wallpapers`，可适配工坊目录。但它的配置/部分状态仍写到游戏根 `UserData/CyberElectronics`，因此只备份 `ModConfigs`、`ModData` 会漏数据。

另有 3 包没有本地 `preview.png`。工坊封面与本地预览要独立获取，缺少本地图片不能判包不完整。

### 6.4 已找到的补丁交集决定组合验证顺序

显式 Harmony 属性中找到 **29 个跨包同名目标交集**；它没有覆盖全部重载、动态目标和手工补丁，表示优先验证线索，不是 29 个已发生故障。

| 优先组合 | 已见触点 | 应验证的实际行为 |
|---|---|---|
| 电子扩展 × 特性扩展 | 物品目标操作、交易价格、买卖回调、行情、拾荒 | 价格与扣款一致、特性只生效一次、物品/仓库状态正常 |
| 电子扩展 × 联机 | 顾客到店/离场、交易、睡觉、容器接受物品、对话 | 真人顾客与自定义 NPC 共存、交易一致、断线和睡觉保存 |
| 物品详情 × 电子/特性/店铺助手 | tooltip、价格显示、手工补丁及原生 Hook | 展示与实际成交一致、设置与输入不互相覆盖 |

联机包还依赖作者的 HTTPS 路由发现与 WebSocket 通道，不只是 Steam 会话；外部服务故障应与模组加载失败分开。它在 `UserData/ProbablyMultiplayer/steam/<SteamID>` 保存安装身份，该目录不能进入默认可分享诊断包。没有额外权限声明的小鼠养殖包也会改变存档中的养殖状态，权限低不等于卸载无损。

完整文件与程序集盘点见证据 E11。

## 7. 产品架构：复用基础设施，替换正式版适配语义

### 当前 v0.1.1 的真实缺口

**当前管理器能选中正式版 EXE，并不是完全识别不到游戏。** 纯净游戏没有旧 Loader 时，启动预处理也会跳过；主要问题是后续消费模型仍旧。

| 当前入口/模块 | 已确认问题 | 保留或替换 |
|---|---|---|
| `mod_workspace.py` | 只枚举 `Mods/Plugins`；外部文件组直接标 enabled，没有工坊和原生开关 | 保留工作区草稿机制，替换布局、库存与状态服务 |
| `ordinary.py` | 停用会生成 remove 并 unlink 目标文件 | 保留本地包事务与恢复，不用于原生开关 |
| `catalog/imports.py` | 以旧目标前缀和裸 DLL 映射，不能理解标准包根及全部资源 | 在原导入安全框架前增加原生包识别 |
| `loaders/melonloader` | 固定加载器提示；存在旧 net6/代理残留时可能执行 IL2CPP 恢复 | 移除服务、命令、UI 与发行依赖；残留识别纳入一次性迁移 |
| `diagnostics/service.py` / `ai/game_prompt.py` | 默认 Melon 日志；AI固定 IL2CPP/MelonLoader、旧排序假设 | 接原生日志，提示由当前环境能力生成 |
| `deployments/config.py` | 当前仅 PSWallpaper 专项配置，通用编辑器未接主页面 | 增加原生与包专属配置来源 |
| 现有 Workshop 页面/旧 Steam 服务 | 未接当前 DesktopApi，仍有 RimCrow/RimWorld 依赖和覆盖 ACF 路径 | 不整体复活；新接最小只读工坊来源 |
| `online/nexus`、`online/api.py`、NexusPanel | 当前在线入口与 `nxm://` 路由仍绑定 Nexus | 用 Steam 工作坊服务与页面替换，不保留双在线来源设置 |
| 现有方案 | 没有完整的原生 ID/工坊来源/顺序合同 | 格式升版；v2 仅作迁移输入，不再走旧适配执行 |

当前真正接入的在线获取仍是 Nexus；这是待移除的现状，不是新版保留项。仓库里有 Workshop 页面、排序图或配置编辑组件，不等于用户主路径已具备这些能力。准确代码定位见 E12、E14。

### 7.1 不重写整个应用，也不继续套用文件部署模型

保持现有 Python 桌面后端、Vue 工作台、异步任务和可恢复文件操作。产品只有一个游戏机制目标，不另建通用多加载器平台：

```text
双列表工作台 / 工坊 / 方案 / 诊断
                  │
原生包与状态服务 ── 依赖图与排序 ── Steam 工坊服务
                  │
本地原生包 / Steam 订阅包 / 可选匿名下载包
                  │
完整包预检 / ES3 字段事务 / 配置与备份 / 启动审计
```

原生格式与获取方式分开建模。匿名取得的工坊内容仍有 Workshop Item ID，但安装为本地原生包，不冒充 Steam 客户端订阅目录；不能仅靠数字目录存在证明当前账号已订阅。旧用户的包库和方案可读取作迁移输入，不能再通过旧执行器部署。

### 7.2 建议的核心数据合同

最小需要新增/拆分：

- `GameIdentity`：AppID、Build、三套版本、后端、游戏/工坊/用户数据根目录、识别证据。
- `ModIdentity`：原生 ID + 来源 + Workshop Item ID/本地安装身份；逻辑 ID 与某次安装实例分离。
- `AcquisitionState`：Steam 账号订阅/匿名下载/本地导入、订阅状态、下载状态、更新时间和证据来源；账号身份与可分享方案分离。
- `NativeManifest`：原始文本、解析结果、DLL 列表、权限、依赖；保留未知字段以便升级。
- `ModState`：`installed`、`desiredEnabled`、`trustState`、`lastLaunchRunning`、`loadError`、`restartRequired`、`shadowedBy`。
- `RuntimeEntry`：包内各 IMod 入口的程序集、初始化/错误记录；包级状态由入口与必需依赖汇总，不丢失部分失败。
- `CompatibilityEvidence`：声明版本、静态引用、补丁/Hook 证据、启动审计、玩法验证分别记录。
- `DependencyEdge`：来源、两端 ID 类型、必需/前后/获取关系、解析结果、原始证据；不混淆工坊合集、包内 DLL 和跨 Mod 依赖。
- `Profile`：目标启用顺序、来源选择、期望版本/内容快照引用、可选配置快照；不包含信任、凭据或默认存档正文。
- `ChangePlan`：本次对象、目标变化、原状态、恢复位置、需要游戏确认的项及完成判定。

对旧字段做有版本的转换；不要把原来“移走 DLL”的 `disable` 偷换为新含义却继续共用相同计划/执行器。

### 7.3 写入责任要分清

| 对象 | 所有者 | PSModManager 的职责 |
|---|---|---|
| 账号工坊订阅与客户端下载 | Steam | 通过已登录会话/官方页面操作并对账；不直接改 ACF/下载目录 |
| 可选匿名下载包 | 管理器独立缓存 | 验证下载完成后按本地包安装，保留来源和更新跟踪；不标为账号订阅 |
| 原生运行、权限批准 | 游戏 | 预检和解释，交原生 UI 确认；以启动结果对账 |
| 本地安装包 | 玩家 / 管理器管理目录 | 暂存完整目录、预检、备份、原子切换、失败恢复 |
| 原生期望状态 | 游戏的 ES3 状态 | 游戏关闭时受控字段级修改；发现外部变更则重新预览 |
| 分享方案 | 管理器 | 分享引用和配置选择，不打包批准/账号资料/未经授权的模组 |
| 存档 | 玩家 | 明确选择下备份/恢复，不随卸载自动清理 |

正式版优先从 Steam 启动。直接 EXE 启动可能触发 `RestartAppIfNecessary`，进程交接不能被误判为启动失败；运行证据应绑定本次启动时间、游戏路径和新日志，而非只盯首个子进程 PID。

### 7.4 可靠的“保存并运行”流程

1. 读取游戏与 Steam 状态，游戏运行时只读盘点，不落盘启停/配置修改。
2. 在本地工作副本中调整目标启用、顺序和来源，显示具体差异。
3. 检查完整包、重复/遮蔽、缺失依赖、循环、原生版本与权限变化；无法满足的目标保留明确原因。
4. 提交前重读涉及文件，比较原始内容/版本状态，确认没有游戏或 Steam 并发改写。备份并建立恢复记录。
5. 仅写已知 ES3 字段和选定配置；停用同步撤销对应记录；不自动补批准。临时文件验证后替换并读回。
6. 提示待批准项，启动游戏并在原生界面完成必要确认；原生要求重启时明确保留这一阶段。
7. 读取新一轮启动审计，将“计划已保存”和“模组已运行”分别结案。没有新日志/未重启时保持待验证。

此流程的 ES3 写入器是首个开发验证重点：当前格式已读懂，但其跨字段原子性、失败恢复和游戏读回尚未实施验证，不能直接跳到真实文件写入。

现有风险账本还保留运行中检测的 **8 个历史失败**，涉及特殊进程路径/硬链接/权限与竞态；它们不是本轮新跑出的结果。原生状态写入启用前须修复受影响的检测路径并定向回归，状态不明时拒写，不靠“通常已经退出”作为并发保护。

### 7.5 MelonLoader 与 Nexus 的退役必须覆盖真实入口

不是仅删两个按钮。实现时沿当前入口完成以下闭环：

1. 移除前端 MelonLoaderPanel、NexusPanel、引导、设置与事件监听，以及后端装配、命令路由、自动修复/下载任务。
2. 移除启动参数中的 Nexus 收件处理、`nxm://` 注册/接收、专属网络白名单、发行资源与打包依赖；保留仍有消费者的通用下载、任务、解压和恢复工具。
3. 迁移时只解除确由 PSModManager 注册且仍指向本程序的 `nxm://` 关联，不修改其他 Mod 管理器的默认处理器。只处理本程序拥有的 Nexus 凭据项，不读取或显示其值。
4. 游戏目录里的旧注入文件先识别来源和占用，再给出可恢复的清理预览。不能凭 `version.dll` 文件名直接删除；不连带删除 `Mods`、`UserData` 或存档。
5. 旧方案 v2 仅做读取与迁移预览：可核验的完整原生包进入新方案；MelonMod/裸 DLL、旧路径和未知项列出无法迁移原因，不猜测转换或自动启用。
6. 同步调整当前使用说明、AI 环境提示、构建配置及针对性测试；历史发行说明与旧验收记录保留历史含义，不批量改写为正式版通过。

## 8. 界面：改为 RimCrow 式双列表，详情与问题按需展开

推荐主路径为：

**选择游戏 → 订阅或导入完整包 → 移入启用列表 → 补齐依赖/调整顺序 → 保存并运行 → 对账启动结果。**

已只读核对 RimCrow 当前源码：它有未启用/启用列表、跨列表拖动、多选、历史撤销、自动排序与规则冲突处理。这里复用交互思路及可独立抽出的组件，不复活旧的环世界 Store、`ModsConfig.xml`、DLC 核心包和 Steam ACF 写入逻辑。证据见 E14。

### 8.1 主界面采用三栏，而非继续扩展卡片库

```text
Probably Stolen · 100-Rev3       当前方案 ▾       Steam 状态       运行游戏
模组工作台   创意工坊   方案与备份   日志诊断
────────────────────────────────────────────────────────────────────────
可用模组                     启用与顺序                  模组详情
搜索 / 来源 / 需处理          搜索 / 自动排序 / 规则       名称、封面、来源
                             01  模组 A                 概览 | 依赖 | 配置
未启用的已安装完整包  ──→     02  模组 B                 权限 | 运行记录
下载中 / 缺失项目占位 ←──     03  模组 C
                             顺序编号 + 独立状态标记      依赖谁 / 谁依赖它
添加本地包 / 打开创意工坊     冲突行直接定位              原因与可执行修复
────────────────────────────────────────────────────────────────────────
待保存变更 · 阻断问题 · 待批准/重启       撤销 / 重做   保存   保存并运行
```

主工作台展示完整 Mod 包，不把包内 14 个 DLL 拆成 14 个模组。

- **左栏“可用模组”**：默认未启用库；来源与下载状态作筛选。名称/更新时间排序只影响这里的浏览，不修改启用次序。
- **中栏“启用与顺序”**：显示当前方案的完整序列和稳定序号；支持跨栏拖入/移出、组内多选移动、上下移动、置顶/置底。搜索只筛视图，不重编号或丢失被隐藏项；有筛选时停用拖拽排序，并提供“清除筛选后调整”。
- **右栏“模组详情”**：按包展示概览、依赖与被依赖、配置、权限和运行记录；多入口展开显示，不重复整包。关系图作为可选视图，默认先给可操作的问题列表。
- **底栏**：持续显示草稿差异；单击定位问题，保存成功只代表原生目标状态写入成功。需要批准或重启时继续显示，不提前变为“运行正常”。
- **大小与可访问性**：双列表优先分配宽度，右详情可折叠；小窗口用抽屉而不是压缩字体。支持 Ctrl/Shift 多选、键盘移动、撤销重做和可见焦点；沿用现有颜色/字体变量，移除妨碍密集排序的花园卡片和“篮子”主交互。

### 8.2 关键操作及其状态变化

| 用户动作 | 工作台行为 | 不应发生的事 |
|---|---|---|
| 将 Mod 移入启用列表 | 已安装的必要依赖一并加入草稿，并列明新增项；缺失依赖给获取入口 | 不自动扩大账号订阅、不伪造批准 |
| 移出被其他项依赖的 Mod | 展示反向依赖，选择同时停用受影响项或取消 | 不悄悄留下失效依赖链、不删除文件 |
| 自动排序/手动移动 | 统一更新一个有序草稿，显示原因/冲突，可撤销 | 不把可见筛选结果覆盖为完整 modOrder |
| 保存 | 预检、备份、写入目标字段并读回 | 不等同于 Mod 已运行 |
| 创意工坊订阅 | 当前账号订阅成功后等待下载，安装完整再进入可用列表 | 不因点击按钮就标为“已安装/已启用” |
| 匿名下载（若可用） | 独立缓存、校验完整包、安装为本地来源 | 不显示“已订阅”，不写客户端工坊目录 |

保存方案草稿与应用到游戏分开；依赖不完整的草稿可保留，但阻止应用和保存并运行。方案切换有未保存修改时，提供保存草稿、放弃或取消，不覆盖当前编辑。

### 8.3 创意工坊是一级页面，不只是改掉 Nexus 的标题

工坊页包含搜索、条目详情、版本/更新时间、作者、必需条目、订阅/取消订阅、下载队列及返回本地工作台。界面顶部区分“账号订阅（通过 Steam）”与“匿名下载（可用性待确认/可用/不可用）”，按钮随实际能力变化。

状态文案使用 `已订阅，下载中`、`已安装，未启用`、`已选择，需在游戏中批准`、`已批准，等待重启`、`本次启动已加载`、`匿名下载的本地副本`。工坊账号未知时显示“订阅状态未确认”，不从磁盘目录推导账号授权。

“停用”“移除本地文件”“取消订阅”“停止本地更新跟踪”分为不同操作。AI 留在日志诊断中，不占固定第四栏，也不成为排序和普通管理的前置条件。

## 9. 工坊、更新、发布及分享

### 9.1 推荐默认：使用用户的 Steam 账号订阅

**账号订阅是主通道，匿名是补充下载通道。** 默认借助已登录的 Steam 客户端/官方工坊页面完成订阅与取消订阅，用户无需把 Steam 密码交给管理器。游戏本身已使用 Steam UGC 会话；这不等于外部管理器天然拥有同一会话。

管理器承担条目发现、依赖预检、下载观察和安装对账。初期通过官方工坊页完成实际账号操作；有经验证的 API 授权后，再把对应动作收进管理器。官方页交接应明确标为“在 Steam 中订阅”，不能伪装为已经完成的应用内授权。

若要求管理器内直接代用户订阅，需要选定并验证正式接入方式：Steam OAuth 确实存在，但须由 Valve 分配 Client ID，Workshop 权限按 AppID 配置；不是普通应用可随意填写一个 Client ID 就启用。[Valve OAuth](https://partner.steamgames.com/doc/webapi_overview/oauth)

Steam OpenID 提供的是登录身份/SteamID，不能将它单独当成工坊代操作授权。也不把个人 Web API Key、网页登录 Cookie 或 `steam_appid.txt` 当作等价替代。[Valve 用户认证](https://partner.steamgames.com/doc/features/auth)

账号变化后重新核对订阅；客户端目录可能保留其他账号下载的内容。没有当前账号证据时展示“本机已安装、订阅状态未确认”。不读取浏览器或 Steam 私有凭据文件来复用登录。

### 9.2 匿名通道：可以评估下载，不能称为匿名订阅

Steam 的 anonymous 不是拥有个人订阅库的默认用户。Valve 文档明确区分订阅与未订阅下载，并以匿名游戏服务器为未订阅下载的例子；匿名缓存不能据此等同于账号订阅。[Valve ISteamUGC：DownloadItem](https://partner.steamgames.com/doc/api/ISteamUGC#DownloadItem)

本轮没有验证 `4348910` 的匿名内容访问能力，不能预设所有公开工坊条目都可匿名下载。后续工坊接入负责人应在独立缓存中，用一个真实公开条目完成匿名下载、读取清单和重复更新检查；访问拒绝就将该模式标为不可用，转向账号官方流程，不尝试绕过访问限制。

若验证可用：

- 按 `AppID + ItemID` 维护独立下载任务和缓存，等完整下载成功再导入本地 `Mods/<包目录>`；不在 Steam 客户端工坊目录伪造条目或 ACF。
- 保留 Workshop Item ID、版本和获取方式，名称显示“工坊来源 · 本地副本”；用户可选择管理器维护的“跟踪更新”，它不是 Steam 云端订阅。
- 显式处理同 ID 的订阅版/本地版遮蔽、更新前备份和来源切换后的重新批准。
- 下载失败、登录过期或权限不足保留原包和草稿；不自动切换账号，也不把部分文件计为安装成功。

当前可先交付账号订阅交接和本地管理；匿名支持与应用内 OAuth 各按其真实证据启用，不拖住其他已具备条件的工作。连接状态与下载状态的数据合同见 §7.2，具体官方依据见 E13。

### 9.3 版本锁定应诚实

Steam 自动更新的订阅目录不能靠管理器改写 ACF 来“锁版本”。需要固定已知版本时，生成玩家选择的本地快照并明确切换来源；提示它会遮蔽订阅副本、改变信任来源，需要重新审阅。联机方案还要记录真实内容版本，不能仅比较清单名称。

### 9.4 作者工具放在后续独立入口

建议先实现“检查包 → 生成干净暂存目录 → 预览发布内容/权限/封面 → 显式发布确认”。排除 `bin/obj`、私有配置、日志、凭据和不应再分发的游戏 DLL；游戏管理器运行仍不应依赖作者工具。

游戏包格式、Steam 上传元数据、PSModManager 的内部方案格式应是三种不同合同。工坊 `PublishedFileId` 不能替代原生 `ID`。

Valve 将 SteamCMD 的上传集成定位于测试用途；独立发布工具可需要游戏方配置发布权限。建议玩家端避免收集 Steam 密码，作者端先提供包检查和发布资料准备，再选择经验证的发布渠道。[Valve Workshop 实施指南](https://partner.steamgames.com/doc/features/workshop/implementation)

社区上传器可作为外部选项，但本次已发现其 `<Mod>` 根元素限制，不能在修正和验证前直接接为默认流程。

### 9.5 方案分享以引用为主

原生方案应优先包含 Workshop Item ID、原生 ID、获取方式、来源、版本、启用顺序、自定义排序规则及用户选择的配置；导入时重新匹配本机安装和信任。默认不把工坊 DLL 重新打包外发，也不导入他人的 Steam 会话、`modTrust`、`workshopOwners`、开发者模式和完整 `SaveFile.es3`。接收者选择自己的账号订阅或可用的匿名通道，不继承分享者的账号授权。

## 10. 诊断与性能：先让证据正确，再做智能解释

### 10.1 原生日志应成为第一来源

新的诊断链：

`本机 Build/来源快照 → 本次 Player.log → ModLoader audit → 加载/扫描/Hook/资源/存档错误 → 操作建议`

至少识别：清单缺失/无效、列出 DLL 缺失、未列 DLL、入口不存在、重复 ID、来源遮蔽、权限变更、拒绝/封禁、依赖缺失、类型加载异常、Harmony 失败、Hook 处理器异常、资源解码失败、工坊未下载、存档 dummy 回退。

“没有 Harmony patch”可能只是正常使用原生 Hook；“依赖 DLL 没有 IMod”可能只是库；旧日志中的 `running=True` 不能证明本次启动。诊断必须结合包角色、日志会话和上下文，而不是关键词一命中就报故障。

AI 提示和工具从原生游戏身份与状态服务取得环境事实，移除固定 IL2CPP/MelonLoader 假设。先跑确定性规则，再让 AI 解释证据；任何修改仍走受控变更计划。给远端 AI 的日志应去除账号标识、凭据和无关个人路径，保留必要堆栈和模组身份。

### 10.2 性能优化围绕真实成本

- 一次枚举形成可复用快照，元数据按来源、尺寸、mtime 和游戏 Build 缓存；显式预检/信任验证时再检查内容。
- 先按名称、版本、来源筛选，再读取程序集或大型资源；沿用现有普通操作的批量事务思路。
- 主线程不反编译，不启动模组。元数据 worker 有超时、错误结果、缓存和取消。
- 工坊预览图异步加载；离线无图不阻塞列表。
- 日志增量读取并识别轮换，不每次 AI 追问重扫全库。
- 大资源包采用数量、展开体积、单文件与路径等分开的限制；当前普通导入已有 4000 文件、64 MiB 单文件/ZIP、256 MiB 展开总量约束，应按真实包测量调整，不简单取消保护。

性能验收采用真实包库的冷/热扫描、单项切换、批量保存和新日志对账测量，再决定是否需要更多优化。

4. 完整目录/ZIP 导入、包预检、同 ID 多来源处理；ES3 目标键写入、原生批准交接、事务备份和恢复。
5. 原生配置与自定义数据目录识别，提供带备份的基本编辑；方案格式升版，现有 v2 仅迁移可核验的原生项。
6. 游戏退出检查、Steam 启动交接、重启后审计对账。
7. 验证改动后的真实桌面关键路径、键盘操作、窗口缩放与退出行为；影响普通使用或写入安全的问题随首版修复。

**交付标准：** 使用真实原生包完成“导入或订阅 → 双列表选择 → 依赖补齐/排序 → 保存 → 原生批准 → 重启 → 运行确认”，以及停用、再启用、来源切换、错误恢复。七个当前样本的空依赖不能证明依赖功能通过，需补充真实有依赖的包；算法测试覆盖缺失、环路和稳定性。真实游戏读回和人工关键路径未完成前，保持 `NOT_RUN/待验收`。官方页面交接、应用内授权、匿名下载分别报告验收结果，不相互替代。

### P2：让管理器比游戏菜单更有价值

自定义排序规则、高级依赖可视化与冲突线索、配置编辑增强、存档快照与方案关联、版本快照、分享引用、联机组合校验、细分诊断和大列表性能优化。基础依赖与排序已属于 P1。应用内 OAuth 订阅在取得所需接入条件后单独验收；官方页面交接仍可独立使用。

桌面验收覆盖现有 WebView 退出残留、普通用户环境、干净机器和 100%/125%/150%/200% DPI 关键路径；P1 已修复并验证的部分复用其证据，P2 只对新增交互和剩余缺口补充检查。正式产品交付时同步版本、发行说明和应用内更新记录。

**交付标准：** 用户能知道为什么不能启用、这次到底改了什么、失败后回到哪里；恢复不会带回已撤销的信任或覆盖无关游戏设置。

### P3：作者工作台与可选运行辅助

干净打包、发布预检、受控发布渠道、可选配置 Schema/运行诊断辅助 Mod。涉及 Steam 发布权限和辅助 Mod 的部分单独验收，不阻塞 P1 玩家版交付。
