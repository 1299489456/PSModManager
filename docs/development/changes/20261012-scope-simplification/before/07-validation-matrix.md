# 07 开发验收矩阵

本矩阵定义需要证明的产品行为，不记录已通过的产品测试。建立日期为 2026-09-28；当前项目尚无产品实现，以下全部用例的验证状态均为 `NOT_RUN`。已有分析报告、历史游戏日志和 DLL 清单用于设计输入，不能替代新产品的运行证据。

范围以 [产品范围](01-product-scope.md)、[数据契约](03-data-contracts.md)、[部署协议](04-deployment-protocol.md)、[诊断与 AI](05-diagnostics-ai.md) 为准。任务依赖见 [路线图](09-roadmap.md)，执行与证据规则见 [验证指南](08-verification-guide.md)。任务状态、用例验证状态、阶段门状态分别维护，不能相互推导为通过。

## 1. 判定与证据约定

- 一个 `CASE` 可以有多个子场景。表格列出的必要子场景全部执行并满足期望，才可记为 `PASS`；缺少必要条件记 `BLOCKED` 或保留 `NOT_RUN`，不能删去子场景后通过。
- `synthetic` 使用自制 DLL、日志、临时数据库和模拟安装目录；`desktop-local` 使用真实应用进程、WebView 与本地临时数据。二者都不读取、改写真实游戏或 RimCrow 数据，不调用真实 AI 服务。
- `real-readonly`、`real-game`、`ai-live`、`release` 必须具有覆盖实际资源、操作与联网范围的授权。会话内已获得且仍适用的授权持续有效，不重复索要；仅提供路径不等于允许写入、启动或外传。
- 基础证据包括版本/提交、命令、环境、输入 fixture 哈希、子场景结果、退出码、完整相关输出。表内“专项证据”是在此基础上的追加要求；保存到 `docs/development/evidence/<task>/<UTC-run>/`。
- “零写入”判定检查受保护目标的文件集合、内容哈希和写入事件；管理器自己的隔离数据目录另行列出。真实游戏自身并发写入应记录为外部变化，不能伪造出扫描前后完全一致。
- 所有截图必须关联运行与动作；截图只能证明可见界面，不能单独证明后端鉴权、文件一致性、玩法生效或断电耐久性。
- 表中的场景规格是最低要求。断电恢复、真实 WebView、真实 provider、干净机器等名称均指对应的实际验证层级，不能由 Mock 或单元测试改名替代。
