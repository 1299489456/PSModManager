# 开发执行、状态与交接

本项目直接使用文档和原生工具开发，不调用 task-doc-generator、task-runner、task-completion-handoff 及该系列技能。任务卡是范围约定，不是自动运行脚本。

2026-09-29 用户调整执行安排：先修当前 UI，准备 M3；新的人工审核统一推迟到 M3/M4 完成后。人工延期不阻止不依赖该人工结论的独立合成开发，但不改写历史失败，不将 G1/G2 自动设为 PASS，也不免除自动验证、实际消费者接线和环境缺口记录。准备阶段不自动执行 M3/M4；真实游戏写入/启动、正式存档、联网或安装依赖的授权边界保持不变。

## 1. 每次执行的顺序

1. 确认用户明确指定的任务ID；读取适用AGENTS、README、台账、该卡与它引用的契约。
2. 检查现有文件和Git状态。初始项目尚未初始化Git；不要把缺Git等同产品失败，也不要擅自提交、创建远程或推送。保护用户修改。
3. 核对前置任务VERIFIED、所需门PASS以及证据仍对应当前代码/输入。未通过时先识别缺口，不跳过验收；可完成不依赖缺口的本卡局部工作。
4. 明确实现范围和最窄验证；多步/高风险改动先写简短实施安排。只修改本卡及必要消费者接线，不顺手重构。
5. 实现、接通实际入口、按卡运行验证并读取输出。源码/测试/harness尚不存在时由责任任务创建；不能先造空入口输出PASS。
6. 失败保留证据，修复后新建run复验。相同失败反复出现时先查根因；不以降标准、删断言、mock真资源或重置数据消除失败。
7. 更新台账、证据和受影响文档；本卡完成即停止，报告下一项就绪程度，不自动执行。

## 2. 唯一状态来源

`task-register.json` 的 task.status 是实现进度，task.verification 是所有必需验证的聚合状态；gate.status 是独立阶段门，三者不混用。

| 任务状态 | 使用时机 |
|---|---|
| TODO | 尚未实施；初始主线全部为此状态 |
| IN_PROGRESS | 正在实现或验证 |
| IMPLEMENTED | 本卡实现和接线完成，必要验证尚未全部完成 |
| VERIFIED | 本卡责任范围所有必需验证通过，有当前版本证据 |
| BLOCKED | 有具体外部条件阻断；保留已实现和已验证的部分，写blocked_reason |
| DEFERRED | M6延后；用户未明确指定不实施 |

verification为NOT_RUN/PASS/FAIL/BLOCKED。VERIFIED必须同时PASS且有证据；PASS不代表验收了其他任务、发布、正式存档或所有游戏版本。未运行进程不填写exit_code=0。

跨任务CASE分别记录当前任务负责的子场景：例如PS-01-04输出依赖事实，PS-02-04才完成计划阻断消费者，不能反过来要求前者等待后者才能验证。基础设施任务按本卡API/存储/进程集成证据验证，不要求尚未实现的未来UI；各阶段收口任务必须补齐实际用户入口。阶段门按完整责任范围汇总，自身不自动触发开发。

证据路径以本目录为基准，例如 `evidence/PS-01-03/20261001T080000Z/summary.json`。台账记录该路径，不复制整段日志。动态CASE结果写run内cases.json；07矩阵中的NOT_RUN是规划初始值，日后不要把静态表当实时结果。

## 3. 命令与依赖约定

当前可运行的是 `tools/Validate-DevelopmentDocs.ps1`。产品命令和测试均是未来任务的交付目标，所有任务卡已标明。PS-00-01负责环境盘点，PS-00-02起使用项目`.venv`里的Python；缺失则报告环境缺口。PS-00-05提供后续统一runner。

包管理命令可能联网或安装，不能在“验证”中隐式触发。`uv run --no-sync`与直接已安装解释器优于自动同步；C#已恢复工程用`dotnet build --no-restore`，需恢复时单独确认已有授权。前端prebuild的间接调用也必须检查。

不新增依赖只为使用惯用测试框架；优先现有pytest、Node内置测试和项目自建桌面harness。必需新依赖在任务内说明用途、版本、许可证和替代方案，取得明确授权后再安装。

## 4. 源码导入与共享文件责任

PS-00-01导入固定参考源码，保留本项目docs；PS-00-02才切断旧业务启动副作用。旧代码可以暂留未接入状态，但新桌面不能触发旧扫描/更新/数据迁移。不在原RimCrow仓库直接改造。

根入口/composition归M0维护，03/04契约归当前改动任务维护；每个后续任务仅增加所需注入/命令路由。多人或子agent工作必须指定文件所有权，禁止同时编辑同一store/API大文件。共享接口先统一再并行。

不把保留MIT声明与全部第三方资产可分发混为一谈。参考仓库第三方依赖和素材逐项记录；不把游戏、Il2Cpp生成程序集或他人模组当测试资源提交。

## 5. 实机与联网

合成/真实桌面临时数据是默认验证路径。真实游戏只读、游戏写入启动、外部AI、在线源和干净VM按08的profile区分。已有仍适用授权继续有效，无须每步确认；超出现有范围才问缺失信息。

取得真实游戏写入/启动授权前，先完成代码、合成回归、具体计划与备份/恢复清单，使需用户决定的内容可审阅。不要以模糊“是否继续开发”阻塞已授权的本地工作。

实机任务中不能确定正式存档/Cloud边界时，保留玩法验证缺口；不要默认使用唯一正式存档或关闭云同步。此规划交付没有进行任何真实部署或启动。

## 6. 文档维护和结束报告

任务拆分/新增时更新卡、台账、09路线、11指令、需求映射和07用例；运行文档检查。原分析报告保留，不回填新结果伪装成历史证据。

结束报告包含：任务ID、实际交付入口与行为、修改文件、验证命令/退出码/计数、证据路径、剩余缺口、相关门状态、下一项就绪情况。不要只报告“代码写好了”。

本规划不要求commit。用户明确要求提交时，按适用AGENTS的Lore协议，精准暂存本任务文件，禁止混入用户修改或真实资源。
