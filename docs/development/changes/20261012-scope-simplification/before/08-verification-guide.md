# 08 验证入口与证据指南

### PS-03-04 synthetic 责任

产品命令为 `pwsh -NoProfile -File scripts/verify.ps1 -Task PS-03-04 -Profile synthetic`。Python CASE-022 覆盖真实接管的首代回退、多个共享 owner 退出、最后 owner 移除及配置/可变/未知文件保护；CASE-034 覆盖真实多代次、回退的回退、外部保全与持久复查、坏/缺失备份、批准后身份/字节漂移、跨安装绑定、真实进程中断恢复、取消、幂等和引用保护，以及真实历史页原生批准入口。相关前置 planner/executor/storage/API 回归分开计数。

Node 只承担 CASE-034 的历史/预览消费者分项，不宣称验证 CASE-022 真实共享文件行为。实际文件、SQLite、MAC、冷启动恢复和真实 WebView 是独立产品证据，构建及 Mock 不替代它们。官方 runner 不支持本卡 desktop-local/real-game Profile；真实 WebView 测试作为本卡 synthetic 的实际消费者运行，依然只使用合成安装及隔离 data root。

本卡独立合成验证可结束本卡责任，G2 的人工及阶段集成仍 BLOCKED，未重新审核的 UI 不继承历史人工通过。实际文件符号链接权限不足、真实游戏/实际 Mod/正式存档、系统 DPI、人审、物理磁盘满、硬件断电、其他文件系统及联网 AI 等范围单列，不改写为 PASS。

PS-03-03 实现说明：当前 `synthetic` 路线显式映射 CASE-029～033 的实际 executor/recovery、journal/native rename、SQLite 迁移及真实 WebView 消费者。其余 Profile 仍拒绝；动态结果以本卡台账和逐次证据为准。产品进程强杀必须验证 marker PID 与实际被持有的 Popen 对象相同，并核对 executable/creation time、确认退出；Windows venv redirector 不能冒充实际 executor PID。首次发现这类错位时保留失败及纠错清点，不能写假 cleanup=0。

Python job 的 `case_tests` 必须包含本卡全部五项责任；Node job 通过显式非空 `node_case_tests` 只记录 CASE-029/030/032 的组件分项，不能要求或冒充 CASE-031 强杀与 CASE-033 journal/DB 对账。没有显式 Node 映射的旧路线沿用原映射；空映射、未知 CASE、空 pattern 或遗漏 Python 必要 CASE 仍拒绝。组件与实际进程/桌面证据分别列示。

受控 checkpoint ENOSPC 与真实 Windows sharing/DACL 拒绝分别记录；真实物理磁盘满、电源中断/设备缓存、真实游戏和玩法均未由 synthetic 验收。自动 WebView/截图不代替人工、系统 DPI 或前序阶段门。CASE-030 的历史用户回滚功能仍属 PS-03-04；CASE-029 的运行验证、CASE-033 的后续能力按各卡分列。

本文件定义开发时如何取得和报告验证证据。规划期的未运行状态不覆盖后续逐次产品证据；动态结果以台账和各次 summary/JUnit 为准。文档校验成功只证明规划文件的结构与引用符合检查规则，不证明产品已经实现。

PS-00-05 实现说明：上面的规划期描述不作为动态状态。当前结果以台账和逐次证据为准。统一入口 `scripts/verify.ps1` 已显式接入 PS-00-01～05 synthetic，以及 PS-00-02/04 desktop-local；其他组合保持拒绝，后续任务完成自身测试后再扩充 [verification-profiles.json](verification-profiles.json)。

报告 v1 的可校验契约为 [verification-summary.schema.json](verification-summary.schema.json)，使用已安装的 jsonschema 校验，不自动安装。`exit_code` 是最后实际命令原始退出码（未启动/超时无法取得时为 null）；`runner_exit_code` 是整体判定码，语义失败为 1、前置阻断为 2、超时为 124，命令非零通常原样转发。`commands` 保留各命令的 started、exit_code、timed_out 与 JobObject 清理结果。`cases.json` 的 v1 `cases` 按 CASE/Profile/job 列出每个 JUnit 子场景及结果；计数只包含测试，不含编译和文档检查。环境 v1 包含依赖版本、隔离根、代码指纹及约束，台账摘要单独记录，状态更新不使代码指纹失效。

写入路径拒绝重解析点、硬链接及歧义路径；证据读取不跟随负例创建的重解析点，另存 `artifact-links.json`。合成 DLL 只由项目自制源码通过已安装 Roslyn 编译，不执行程序集；当前最小样本是 3 个 Mods DLL 和 1 个属性依赖，并不代表历史 45/43 样本已实现。Windows JobObject 约束执行及后代生命周期，不宣称网络或低权限沙箱。

高风险授权配置 v1 必须包含 `task_id`、`profile`、`resources`、`operations`、`network`、`upload`、`budget`、`valid_until`（带时区且未过期）、`excluded_data`；不得保存凭据。尚未接入的高风险执行路由即使配置完整也拒绝执行，不以文件替代会话授权。常规 synthetic/desktop-local 使用已授权的项目内隔离资源。

PS-01-07 补充：已接入明确授权的 `real-readonly` 路由，使用与合成验证相同的真实 WebView 操作流程。授权配置仅记录已有会话许可，不自行产生权限。只授权安装根时 `steam_manifests=[]`，宿主关闭根外清单探测；日志目录枚举与可读档案逐项登记，新增未授权档案拒绝读取。独立数据根保存 SQLite 和证据，登记范围前后完整哈希比对；审计钩子属于额外保护，不宣称完整操作系统沙箱。真实游戏启动、写入和其他高风险 Profile 仍不由此开放。

用例见 [验收矩阵](07-validation-matrix.md)，状态和依赖见 [任务台账](task-register.json) 与 [路线图](09-roadmap.md)，逐项开发的范围与停止条件见 [执行指南](10-execution-guide.md)。

## 1. 当前与未来命令分开

当前可运行的入口是本次配套文档工具：

```powershell
pwsh -NoProfile -File docs/development/tools/Validate-DevelopmentDocs.ps1
```

在 `E:\WorkSpace\ForTools\PSModManager` 下运行。它不启动产品、不运行游戏、不执行模组 DLL、不安装依赖。记录其退出码与报告，但不要把结果填入产品用例或 G0～G5。此命令本身是否已执行，以对应运行证据为准，不能仅因出现在文档中视为通过。

PS-00-01～PS-00-04 尚不能依赖统一产品 runner；按各任务卡列出的本地直接命令核对导入、命名空间、迁移和实际桌面桥接。执行前确认对应源码、fixture 与工具已存在；缺少时记录 `NOT_RUN/BLOCKED`，不要用空脚本填补。PS-00-05 负责建立并验证未来统一入口：

```powershell
pwsh -NoProfile -File scripts/verify.ps1 -Task PS-01-03 -Profile synthetic
```

上例是未来命令规范，当前不保证文件存在。runner 建成后，每个任务可支持一个或多个 Profile，按本矩阵选择；不支持的组合必须明确拒绝。任何执行路径都不得自动执行 `pip install`、`npm install`、`npm ci`、`dotnet restore` 等依赖获取动作。缺依赖时报告名称、所需版本、用途与当前缺口，依赖安装按单独授权处理。

## 2. Profile 与资源边界

| Profile | 允许的验证输入与动作 | 必要前提 | 不能推导的结论 |
|---|---|---|---|
| synthetic | 项目内自制 fixtures、一次性临时目录/数据库、模拟进程与服务，执行隔离产品代码 | 固定输入哈希，写入范围可枚举；worker 负例也只能触及受控哨兵 | 不代表真实游戏、真实 WebView、断电持久化或实际 provider 通过 |
| desktop-local | 真实应用进程与 WebView、真实桥接 API，使用临时安装树与测试数据 | 独立应用数据目录，关闭外部服务，明确 UI/harness 入口 | 不代表真实游戏效果、真实存档或干净机器发行能力 |
| real-readonly | 指定真实游戏/日志/安装 manifest 的只读发现和对照，管理器索引写到隔离目录 | 当前任务明确授权具体路径、读取内容及证据保存范围；验证游戏树无写入 | 不授权启动游戏、接管为可写、更新加载器或外传真实 DLL |
| real-game | 对已授权测试安装应用具体计划、启动、观察、回滚；必要时使用指定可丢弃存档 | 明确目标安装、计划范围、备份/恢复、存档与 Steam Cloud 边界、允许的启动与玩法动作 | 不授权其他安装、正式存档试验、无边界反复修复或更换系统运行时 |
| ai-live | 对指定 provider 发送获准的脱敏样本，验证真实请求/工具/计划闭环 | 明确 provider、联网目标、输入范围、凭据获取方式、费用/时间预算；部署仍使用已授权环境 | 不授权上传全部日志/游戏 DLL/存档，也不自动扩大文件写权限 |
| release | 构建与审计发布产物，在指定干净机器或隔离 VM 验证便携/安装态、迁移、存储中断 | 明确机器、产物、允许的构建/执行/联网/故障注入范围；依赖预先就绪 | 不授权对外发布、签名凭据使用、自动下载前置条件或在玩家设备断电 |

后四种 Profile 的授权需要可追溯且覆盖当前资源和动作；本会话已有且仍适用的授权持续有效，不重复询问。用户仅提供路径不等于同意写入、启动或传输。可以继续不依赖这些授权的合成实现与检查；授权不足时才请求缺失范围。

授权输入应至少包含任务、Profile、目标资源、允许操作、联网与数据上传范围、预算、有效范围及禁止触及的数据。其机器可读结构由 PS-00-05 在 runner 中固化；不得把凭据本身写入授权文件或证据。

## 3. 每次运行的证据目录

使用 UTC 时间标识，避免本地时区歧义和覆盖旧失败记录：

```text
docs/development/evidence/<task>/<UTC-run>/
  summary.json
  environment.json
  command.txt
  stdout.log
  stderr.log
  cases.json
  inputs.sha256
  artifacts.sha256
  artifacts/
```

`<UTC-run>` 建议采用 `20260928T083000Z`，并发运行可增加随机后缀。真实数据与完整日志默认保存在本机受控位置；进入共享仓库的证据须脱敏并经过范围审查。不要把真实 DLL、完整游戏目录、存档、API key 或私人路径自动提交或上传。目录存在不等于证据有效；必须检查文件可读、数量、哈希和内容完整性。

最低证据内容如下：

| 文件或内容 | 最低要求 |
|---|---|
| summary.json | `task_id`、`profile`、`run_id`、`verification_status`、`started_at`、`ended_at`、`command`、`exit_code`、版本/提交、测试发现/执行/通过/失败/跳过数、必要 case 列表、阻断与缺口、证据文件引用；字段使用snake_case |
| environment.json | Windows/架构、应用/worker/runtime/WebView 版本、依赖版本、代码与脏工作区指纹、隔离目录标识、资源/网络约束；不能含密钥 |
| cases.json | 每个 CASE 及必要子场景的状态、期望、实际、Profile、fixture/产物哈希、原始输出位置、失败原因；同一 CASE 跨 Profile 的结果分列 |
| command.txt 与输出 | 完整且已脱敏的命令、工作目录、真实退出码、相关完整输出；输出截断需保留本地原件引用，不能省略导致失败的部分 |
| inputs.sha256 | fixture、源日志片段、待测产物、故障脚本等输入标识与哈希；需要确定来源而又不能外传时使用本机引用并记录访问边界 |
| artifacts.sha256 | 报告、journal、manifest、截图、构建包等交付证据的哈希及相对位置；避免把本文件自身纳入循环哈希 |
| artifacts/ | 用例要求的 DB/文件对账、故障点覆盖表、实际桥接记录、脱敏请求摘要、干净机器记录等；大型或敏感文件可保留本机受控引用 |

JSON 报告的最终 schema 由 PS-00-05 落地并版本化，字段名若需调整须同步本指南及消费端。示例状态语义不得改变。进程未启动时 `exit_code` 应为null并说明原因；不要填写 `0`。缺少 Git 仓库或 HEAD 时明确记录当前文件摘要，不能捏造提交号。

## 4. runner 必须遵守的判定规则

1. 先解析任务与 Profile，再确认任务映射、源码、fixture、依赖、必要用例和资源授权。缺少条件必须在执行前报告。
2. 精确选取当前任务与必要回归；打印实际命令并转发真实退出码。runner 不得把子进程异常吞掉后返回成功。
3. 测试发现数与执行数均可核对。框架报告 `0 tests`、入口不存在、必要测试全跳过、测试进程未启动，均不能 `PASS`；runner 必须非零退出并产生 `BLOCKED/FAIL/NOT_RUN` 中适当结果。
4. 每个必要 CASE 在本任务责任范围内的全部必测子场景有明确结果。单元测试不能替代必要桌面/游戏子场景；CASE-031中明确列为扩展的硬件断电实验单独记录，不混入首版必测通过数。
5. 所有产物落在本次证据目录，失败运行不得被后续成功覆盖。复验生成新 run，引用前一失败 run 与修复内容。
6. 退出码为 0 是命令成功的必要证据，不足以证明需求已实现。还需核对断言含义、实际消费者、用例覆盖和约定的不变量。
7. runner 因自身错误无法可靠收集结果时，应 `FAIL` 或 `BLOCKED`，不能仅凭最后一条“完成”日志给 `PASS`。
8. 不隐式启动未授权真实资源，不安装/恢复依赖，不把任意输入目录解释成可清理临时目录。清理仅限本次创建并验证位于工作区受控根下的路径。

PS-00-05 应为以上失败分支建立 runner 自检。其他任务不必反复运行全部 runner 自检，但修改测试发现、状态聚合、执行入口或授权逻辑后必须复验相关分支。

## 5. 验证层级如何配合

| 层级 | 适用行为 | 必须补充的上层验证 |
|---|---|---|
| 文档结构 | 任务唯一性、依赖、状态枚举、链接、必要字段 | 不能转化为任何产品实现或运行状态 |
| 单元/属性/解析测试 | 身份、路径约束、图规则、日志分块、计划校验 | 需要真实文件、进程、DB 的相关集成验证 |
| 合成集成 | worker 边界、库存、导入、事务、恢复、迁移、AI 后端拒绝 | UI 任务需实际 WebView；真实运行与发布任务需对应环境 |
| 实际桌面 | WebView→后端→事件→UI、交互、取消与生命周期 | 不自动覆盖真实游戏、实际 provider、干净机器 |
| 真实环境 | 获授权只读比对、游戏、provider、隔离存储故障 | 保留具体版本与资源边界，不推广成所有机器或模组都兼容 |
| 发行验收 | 固定哈希发布包在干净机器运行、缺依赖提示、迁移与回退 | 对外发布与签名是后续独立动作，需要对应授权 |

对文档和低风险配置调整，运行结构/解析检查与 diff 审查即可；不要为可逆文案变化新增镜像实现的测试。影响安全、执行或数据契约时，先运行最窄相关用例，再按影响范围扩展。相关检查已通过且没有新变化或未解决风险时，不无理由重复昂贵测试。

## 6. 关键专项的证据标准

### 6.1 45/43 基线与扫描覆盖

固定历史样本的事实是 45 个 DLL、44 个带 MelonInfo、按已知 v0.7.3 规则预测 43 个直接加载程序集；历史日志的 43 个哈希来自当时样本。合成回归使用自制同等元数据表达这些关系，不复制未经许可的真实二进制。

真实只读验收必须列出每个文件的路径标识、SHA256、解析结果、预测角色与历史加载匹配。发现新增、移除、哈希变化、日志过旧或 Loader 版本变化时，记录漂移并更新“本次实际值”；历史预期作为独立输入保留。新版本 Loader 未取得规则证据时，不能直接沿用旧策略并宣称确定。读取失败、目录无权限或取消导致的部分库存不能当作完整扫描。

### 6.2 worker 解析边界

静态解析测试除确认没有 `Assembly.Load` 等执行行为，还必须验证独立进程、资源上限、超时终止及恢复。低权限、无网络等措施必须有操作系统或等效强制边界及负例；“代码没有主动联网”不等于“无法联网”。若某安全边界受宿主环境限制尚未落实，应记缺口而不是泛称已沙箱化。自制带副作用 DLL 只交给解析器，不主动运行其中代码作为验证手段。

2026-09-29 已实测 Windows 下 `Environment.FailFast` 附加故障注入会由 `csrss.exe` 代弹 `dotnet.exe - 系统警告 / Unknown Hard Error`；进程局部错误模式与 WER 禁止 UI 标志未能阻止它。该诊断保留在 `tests/diagnostics/manual_metadata_failfast.py`，不再随日常 synthetic 路由自动触发，且需显式 `PSMM_DIAGNOSTIC_ALLOW_SYSTEM_DIALOGS=1` 才允许执行。原失败证据见 `evidence/PS-01-07/20260929T010932Z-ui-feedback/dotnet/wer-once.json`。这项系统弹窗行为仍为已知限制，不能计入无弹窗通过数。正常路由继续验证真实子进程硬终止、超时、取消、清理和继续解析；不能把这些替代证据说成 WER 故障路径无弹框，也不能通过修改机器级 WER 策略或放宽隔离掩盖问题。

### 6.3 文件事务与持久化

故障点列表从 [部署协议](04-deployment-protocol.md) 的每个持久化边界生成，至少涵盖 journal、备份、暂存、替换/移除、校验及数据库提交前后。每个故障点需要独立临时安装、输入哈希、结束方式、journal 和恢复后对账；必须覆盖多文件包、共享配置与 DB/文件不同步。

异常注入证明错误处理；强制结束进程证明进程崩溃恢复；隔离 VM 或专用环境实际存储中断用于验证持久化耐久性。三者不能互相改名替代。不得在用户真实设备断电、耗尽真实系统盘或关闭安全软件。磁盘满/占用等先用受控文件系统或故障层注入；实际存储验证在获授权隔离环境完成，并明确剩余硬件适用边界。

恢复成功要求目标文件、manifest、DB 代次与 journal 最终状态对齐；检查“日志打印 recovery complete”不充分。外部修改出现时需证明原内容已保全，之后才进入冲突决策；强制覆盖得到的整齐目录不算安全回滚。

### 6.4 真实游戏与玩法

运行之前记录目标安装指纹、批准计划、原始文件清单、备份校验、预期恢复方式、实际存档路径与 Cloud 状态。没有确认隔离范围时，仅执行授权覆盖的动作，保留玩法缺口；Profile 克隆本身不是存档隔离证据。

运行之后分别记录“文件已部署”“进程已启动”“预期程序集加载”“内容注册”“到达主菜单”“指定玩法动作通过”。没有观测来源的层级保持待验证。若测试目标是修复自停用，必须出现对应新会话、预期版本与未再自停用的证据；仅删除旧 ERROR 文本或复用旧日志不能通过。

### 6.5 AI 与数据外传

使用可控 provider 替身覆盖越权、超时、预算、注入与错误分支，再进行获授权真实 provider 验证。后台执行器必须拒绝伪造工具、越界 evidence_id 与伪造批准，测试不能只断言模型回复“不可以”。真实调用记录脱敏请求摘要、provider 请求标识、预算与最终结果，不保存密钥。

真实 AI 计划的文件写入仍必须通过同一部署批准、预检、journal 和验证路径。调用 provider 的授权不等于允许修改游戏。没有联网授权时可完成替身层和本地 UI 层，将 `ai-live` 子项保留为 `NOT_RUN/BLOCKED`。

### 6.6 发行与迁移

绑定实际产物 SHA256、构建输入和机器环境。干净机器应能说明是否预装 WebView2、worker runtime 或其他前置条件；分别测试存在与缺失情形。开发机上的源码启动、前端静态页面与测试替身不能替代发行产物。

迁移演练使用前一支持版本实际生成的数据或经过明确来源验证的固定数据集，包含版本锁、未知字段、失败事务与损坏备份。先证明备份可读，再升级和回退。不能通过删除旧库、清空包库或手工改 version 字段把失败修成通过。完成本地发行验收不自动触发 commit、push、签名、上传或发布。

### PS-01-07 只读工作台入口

`scripts/verify.ps1 -Task PS-01-07` 已精确映射三种 Profile：`synthetic` 检查基线/授权边界及前端控制器，`desktop-local` 启动实际 WebView、实际后端与隔离 SQLite，通过合成安装验证主流程，`real-readonly` 必须额外提供已获用户授权的 `-Authorization` JSON。配置文件只记录既有授权，不能创造授权；缺配置时退出码为 2，启动命令数为 0。

只读配置以 `scripts/verification/readonly.py` 的显式字段和常量为准：任务/Profile、有效期、只读操作、禁止联网/上传、文件/字节/时间预算、排除存档/凭据/个人数据，以及安装根、三库存目录、必要指纹文件和逐项日志范围。位于 Steam 库的安装还需显式登记发现服务读取的两个库清单路径。完整登记范围在扫描前后核对哈希，不追踪链接。实际解析器会在隔离 data root 暂存输入；残留必须报告，不能把真实 DLL 当作可分享证据。

项目归档中的 45 个物理文件哈希与 43 个历史报告加载项保留原样，历史日期固定为 2026-09-24。归档附带原始日志仅含 6 条加载哈希，不能把报告中的布尔标记充作完整 43 条日志。实机漂移输出 added/removed/changed，不改历史预期。当前真实资源验收入口的直接 API/哈希核对也不能替代真实安装在工作台中的操作；真实 UI 未验收时 CASE-021 不通过。

桌面证据分别记录窗口/client 尺寸、OS DPI 与 WebView zoom。125%/150%/200% WebView zoom 截图不等于该倍率的 Windows DPI 验收。前端控制器性能测试、真实 WebView 行为、参考截图对照与实机验收分别报告，不互相替代。

## 7. 状态更新与阶段门

| 维度 | 状态 | 含义 |
|---|---|---|
| 任务 | TODO | 尚未开始实现 |
| 任务 | IN_PROGRESS | 正在当前任务范围内实现或验证 |
| 任务 | IMPLEMENTED | 代码与接线已实现，但必要验证尚未全部通过 |
| 任务 | VERIFIED | 本任务全部必要 CASE/子场景具备匹配版本的 PASS 证据 |
| 任务 | BLOCKED | 必要实现或验证因具体外部条件无法继续，记录阻断与已完成范围 |
| 任务 | DEFERRED | 规划中明确延后，未授权进入当前实施范围 |
| 用例/验证 | NOT_RUN | 尚未执行，或已有证据不适用于当前待测版本 |
| 用例/验证 | PASS | 全部必要子场景已执行且符合可判断期望 |
| 用例/验证 | FAIL | 已执行并得到违反期望的结果 |
| 用例/验证 | BLOCKED | 因缺少环境、授权、依赖或输入无法完成必要执行 |
| 阶段门 | NOT_RUN / PASS / FAIL / BLOCKED | 独立汇总该阶段必要任务与用例，不从文档存在或任务计数自动继承 |

阶段门 G0～G5 在对应阶段最后一个任务后汇总，完整条件见 [矩阵阶段门](07-validation-matrix.md#9-阶段门汇总规则)。任务的 `VERIFIED` 不等于对外发布批准；G5 通过也不包含对外发布动作。某项合成测试已通过而真实必要子项未执行时，保留子项差异，任务可记 `IMPLEMENTED` 或按阻断情况记 `BLOCKED`，不能写成“已验证，真实环境除外”。

代码、契约、依赖、游戏指纹或验证输入变化使证据不再匹配时，应标记受影响用例待复验，并记录旧证据的有效范围。无需抹掉已有成功或失败记录；新结果以新 run 关联替代关系。

## 8. 单任务完成报告模板

```text
任务：PS-xx-xx
实现状态：TODO / IN_PROGRESS / IMPLEMENTED / VERIFIED / BLOCKED / DEFERRED
本次修改：文件与实际行为；保留的公共边界
已执行：命令、Profile、代码/产物版本、发现/执行/通过/失败/跳过数、退出码
验证结果：各必要 CASE/子场景的 PASS / FAIL / NOT_RUN / BLOCKED
证据：docs/development/evidence/<task>/<UTC-run>/summary.json
未验证：具体环境、授权或行为缺口；不得写成通过
阶段门：相关 G0～G5 状态及是否需要重新汇总
剩余工作：本任务需要继续处理的事项
后续任务：仅说明依赖就绪程度，不自动执行
```

验证失败时先保留原始证据，再定位原因和修复。相同失败重复出现时应检查根因、输入与环境，不反复重跑期待偶然通过。最终结论必须能由当前版本、实际输出和完整必要用例支持。
