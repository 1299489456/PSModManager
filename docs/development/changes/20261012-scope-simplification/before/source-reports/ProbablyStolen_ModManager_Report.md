# Probably Stolen 模组管理器：RimCrow 适配与改造分析报告

**分析日期：2026-09-24**  
**样本：用户提供的 `RimCrow.7z`、`Probably Stolen Demo.7z`**  
**推荐方案：裁剪式 fork——保留 RimCrow 的界面、交互、基础服务和 AI 会话，重建 Probably Stolen / MelonLoader 领域内核。**

配套文件：`ProbablyStolen_Audit_Evidence.md`（E01—E15 源码、日志和核验证据）、`ProbablyStolen_Mod_Inventory.json`（45 个 DLL 的元数据和 SHA256）。本文中的 E 编号对应证据文件；W 编号对应文末核对过的官方资料。

## 一、结论与决策建议

这个项目值得做，而且已有样本表明，它的价值远超“给 Mods 文件夹做一个开关界面”。目前游戏包中已经存在内容框架、二次加载的物品包、同名程序集的版本遮蔽、旧新内容并存、自停用保护、跨模组反射注册以及 Harmony 兼容总线。一个懂这些结构、能解释运行结果、能安全试验和回滚的管理器，会明显减少玩家手动排查。

**推荐选择：从给定 RimCrow 快照建立独立 fork，裁掉 RimWorld 专属业务，接入新的游戏适配层、部署事务层和诊断层。** 不建议仅全局替换名称、路径、Steam AppID，也不建议为了换成另一套桌面技术而从零重写全部交互。

| 路线 | 能保留的价值 | 主要问题 | 判断 |
|---|---|---|---|
| 只换名称、图标、游戏路径 | 很快看到相似界面 | 扫描、排序、启停、日志语义仍是 RimWorld，容易出现“界面成功、游戏未生效” | 不可作为正式方案 |
| 裁剪式 fork | 大部分交互模式、基础服务、AI 会话和卡片体验 | 需要重做游戏领域模型及文件部署闭环 | **优先推荐** |
| 只借鉴 UI，完全新写 | 架构自由、可统一团队技术栈 | 重复建设列表、状态、配置、任务、AI、打包和维护体系 | 仅在长期团队栈明确不接受 Python/Vue 时考虑 |
| 立即改为通用多游戏平台 | 未来扩展空间 | 目前只有一款游戏的需求，过度抽象会延迟核心验证 | 先保留小型适配接口，不做完整平台 |

产品应承诺的是：**知道装了什么、知道实际上加载了什么；对已知问题给出有证据、可撤销、可验证的处理方案。** 不应承诺“AI 能即时修复任何 DLL Bug 或存档问题”。

## 二、本次检查范围和可信度

已完成压缩包解包、项目结构与关键调用链检查、游戏根目录/配置/日志分析、45 个模组 DLL 的 PE/CLI 元数据字节解析、程序集名/版本/MelonInfo/优先级/资源名提取、SHA256 交叉核验，以及与 MelonLoader v0.7.3 官方源代码的规则对照。没有通过 `Assembly.Load` 执行模组，也没有启动游戏。

RimCrow HEAD 为 `a7e875112a175a914bb4706a82589d96d62adc70`，版本文件为 **0.24.7**；其 `__build__` 值仍是 `dev`。忽略行尾差异后，工作树与该提交没有内容差异输出。本报告据此分析上传快照，不宣称它是截至今日所有开发分支中的最新版本。[E01]

统计范围内，后端有 111 个 Python 源文件、68,101 行；前端 `src` 的 JS/Vue 合计 180 个文件、65,067 行。`backend/api.py` 单文件约 9,004 行，意味着存在值得拆分的业务耦合，而非可以随意替换的小型外壳。行数包含空行、注释，不等于有效功能量。[E01]

测试方面，静态识别出 61 个 `test_*.py` 文件、853 个 `test_` 函数，**不能把它们写成“853 项测试已通过”**。本次 Python AST 检查未发现语法错误；一个独立前端 `modIdentity.test.mjs` 脚本执行退出码为 0。所尝试的 Python 测试在收集阶段因审查环境缺少 `vdf` 依赖而中断；未验证完整依赖安装、Windows 打包、GUI 或游戏端到端运行。依赖不足不是项目业务缺陷。[E14]

## 三、游戏包揭示的真实运行结构

### 3.1 基线环境

| 项目 | 上传样本中确认的值 |
|---|---|
| 游戏目录名 | Probably Stolen Demo |
| 实际启动文件 | `Probably Stolen.exe` |
| 游戏报告版本 | `0.46D` |
| 引擎 | Unity `2021.3.45f2` |
| 游戏类型、架构 | IL2CPP、x64 |
| 加载器 | MelonLoader `0.7.3 Open-Beta` |
| 加载器托管目标 | `net6.0`，运行时配置请求 `Microsoft.NETCore.App 6.0.0` |
| 后续模组诊断记录 | `.NET 6.0.36` |
| 根目录 Mods DLL 数 | 45 |
| 最近日志直接加载程序集数 | 43；全部 43 个 SHA256 与现有 DLL 相符 |
| UserLibs / Plugins | 目录存在，该次日志均为 0 个加载 |

依据：`MelonLoader/Latest.log` 第 111—138 行、加载段、`MelonLoader.runtimeconfig.json`、自定义启动诊断日志。[E02、E03、E06]

外部官方商店中，Demo AppID 为 **4349200**，本体 AppID 为 **4348910**，不能混用。管理器仍应读取本机 Steam 库及 appmanifest 来定位真实安装目录，并保留用户手选目录；商店 ID 不代替本地安装验证。[W01、W02]

`0.46D` 不是可以直接交给严格 SemVer 解析器的标准版本串。游戏版本、Steam buildid、Unity 版本及关键二进制指纹应分别保存，不能拿一个比较函数处理所有版本。

### 3.2 45 个 DLL 为什么只出现 43 个加载程序集：现在能够解释

MelonLoader v0.7.3 的 `MelonPreprocessor` 并不是把每个 DLL 都当作独立模组。其预处理会过滤没有 MelonInfo 的托管程序集，并按 **AssemblyName.Name** 汇总，同名时保留较高 **AssemblyVersion**。[W03]

对上传的 45 个 DLL 按这段官方规则推演：44 个带 MelonInfo，其中两个使用同一个程序集名，最终保留 43 个。**预测文件集合与日志集合完全一致，且这 43 个日志哈希与现有文件全部一致。** 这不是本次实际运行游戏，而是规则、样本和历史运行证据相互印证。[E03]

第一种特殊文件是 `PSItemPack_SanmuShiwushechipinPack1.dll`：没有 MelonInfo，却带有 `ItemForge.items.json` 及图标资源。`ItemForgeRuntime.dll` 中有 `PSItemPack_*.dll` 和 `ItemForge.items.json` 的查找标记，日志第 555 行明确记录对应“食物奢侈品拓展包”的 21 个配置已读取。因此应显示为“由 ItemForge 加载的内容包”，而不是“加载失败”。[E04、E05]

第二种是同名程序集遮蔽：

| 文件 | AssemblyName | AssemblyVersion | MelonInfo 显示名称 |
|---|---|---|---|
| `RatColonyOptimizer.dll` | RatGeneticRenamer | 1.0.0.0 | Rat Colony Optimizer |
| `RatGeneticRenamer.dll` | RatGeneticRenamer | 2.6.3.0 | Rat Genetic Renamer |

按当前官方规则，后者优先，前者不会作为另一个独立模组进入直接加载集合。应显示“被同名更高程序集版本覆盖”。**这不证明二者功能完全等价，也不意味着可以自动删除低版本文件。** 用户可能实际想使用另一变体，应通过测试配置选择、重启和验证决定。[E03、E04、W03]

这两个实例足以说明：管理器至少需要独立表达“独立模组、内容包、被覆盖变体、未识别文件、真实失败”，不能只做一个布尔 `enabled`。

### 3.3 文件名、程序集名、显示名和版本不能混为一谈

| DLL 文件名 | 程序集名或显示名中的差异 |
|---|---|
| `PSPDA.dll` | 显示名称为 Terminal，MelonInfo 版本为 0.5.66 |
| `WagesPerks.dll` | 程序集名是 JacksonPerks；日志冲突提示也使用 JacksonPerks |
| `moreUpdate.dll` | 程序集名是 MoreDeviceUpgrades |
| `XIAOWO-WRDUnlock.dll` | 程序集名是 NetworkUnlockEffective |
| `3低概率2%.dll` | 中文和百分号文件名，不能用简单英文 ID 正则代替文件路径 |
| `Nested Storage.dll` | 文件名包含空格 |

身份索引应包含：**原始文件名 → 文件哈希 → 程序集名/版本 → MelonInfo 名称/作者/版本 → Harmony owner → 内容框架包 ID**，同时记录映射来源及可信度。后两种可能需要运行证据或作者清单补足。

例如 AI 看见 JacksonPerks 后，应该定位到现有 `WagesPerks.dll`，不能凭空生成一个删除 `JacksonPerks.dll` 的动作。本次扫描中，45 个 DLL 的 AssemblyRef 没有直接指向其他这批模组的程序集名；但日志明显出现跨模组注册。因此 **AssemblyRef 只能发现一部分编译依赖，不能替代逻辑依赖图**。[E04、E06；完整 inventory]

### 3.4 已有一个真实自停用，而不是所有警告都有故障

`Latest.log` 第 1016 行报告：**“烛印会与失灯区”本次运行已停用，检测到旧版两个 DLL。** 当前目录中同时存在新版 `JCuratedVisitors.dll`，以及旧体系的 `PSItemPack_CuratedVisitors.dll`、`PSCharacterPack_CuratedVisitors.dll`。这两个旧组件是优先核实的关联候选。[E04、E06]

更值得注意：新版元数据为 **1.0.9**，二进制内部启动说明也提到 1.0.9，但报错文案仍写“启动 0.5.0”，其专用诊断日志头也保留 0.5.0。**不能将旧日志模板当作版本权威，自动建议降级为 0.5.0。**[E05、E06]

建议的安全排障流程是：识别准确文件与哈希，备份当前部署和相关数据，建立测试配置；核对作者升级说明后，只在测试配置中隔离旧组件；不动其他作者的模组；重启后验证新模组不再自停用；内容或存档兼容性仍需实测。管理器配置克隆不等于存档隔离，绝不能直接打开唯一正式存档来试验。

### 3.5 兼容性提示必须分级

`XIAOWO-TradePerks` 自报去重了 62 个相同 Harmony 补丁，并报告“共享方法 46、潜在冲突 21、确认冲突 0、停用模块 0”。这是该模组的诊断结果，不是本审查独立证明所有玩法都无冲突。[E06]

因此不应把“21 个潜在冲突”描述成“21 个模组必须禁用”。同样，`XIAOWO-PrecisionBayExpansion` 的 INACTIVE 信息表示检测到主模组后主动交由主模组控制，和崩溃、缺失依赖不是一回事。末尾一次 `DialogUIManager.Instance 为 null` 警告也不足以独立证明持续性游戏故障。

诊断输出至少分为：确定失败、被替代/委托、未验证兼容风险、已恢复问题、信息提示、仍需玩家验证。

### 3.6 环境故障会恢复，不能盯着第一条 ERROR 不放

日志开头确实出现 .NET domain 初始化失败，但随后下载并运行 .NET 6 安装程序，加载器和模组继续启动。后续专用日志记录实际托管环境为 .NET 6.0.36。[E02、E06]

HostFXR 路径中出现 10.0.11，不等于游戏最终运行在 .NET 10；这份日志安装后仍显示同一路径。正确结论是“该次启动早期失败，随后恢复”，不是“必须删除 .NET 10”。

.NET 6 已于 2024-11-12 结束官方支持，应展示维护风险，制定加载器升级测试，而不是忽略风险或直接强迫替换到最新运行时。管理器自身及独立扫描辅助程序可使用受支持的运行环境；**不能因此随意更改游戏加载器的 runtimeconfig 或跨大版本滚动设置。**[W07]

## 四、RimCrow 真正值得借鉴的部分

### 4.1 UI 的价值是工作流，不只是配色

上传项目的主界面图片显示了模组详情、未启用列表、已启用列表和临时/分组/备份工作区的高密度组织；截图本身为较早的 0.23.4，不应把截图标号当成源码版本。源码中可见虚拟列表、搜索筛选、多选、批量操作、分组、快捷操作、历史状态、详情和诊断入口。[E01；`doc/assets/主界面.png`、前端相应模块]

值得保留的体验是：不离开主界面就完成“定位模组—理解关系—调整方案—查看变更—应用或撤销”。相比把每个功能拆成单独向导，这更适合大量本地模组的整理和排障。

面向 Probably Stolen，应把中心列表改成“当前配置计划 + 实际运行状态”，把右侧工作区逐步扩展为“问题、AI 会话、变更计划、部署历史”。拖拽仍可用于分类和显示顺序，但不能冒充可以随意控制 Harmony 补丁顺序。

### 4.2 技术栈适合复用，没必要先换框架

快照使用 Python 3.11+、pywebview 桌面壳、Vue 3 / Pinia / Vite / Tailwind 前端，配合 SQLite/Peewee、Pydantic、AI 网关与系统凭据封装。现有 Vue 交互可以继续使用；游戏代码是 C# 并不要求管理器也全部使用 C#。[E08]

二进制元数据分析可选择 Python 库，或另建一个只读 C# 辅助程序输出 JSON。后者可使用 `System.Reflection.Metadata`/`PEReader`，但必须注意：**不执行 DLL 不代表解析任意恶意文件就绝对安全**。Microsoft 文档明确提醒 PEReader 对恶意/畸形输入存在崩溃、挂起等风险。因此辅助程序应低权限、独立进程、无网络、限制文件大小/耗时/内存，崩溃时不能拖垮管理器。[W08]

### 4.3 AI 不只是聊天框，但能力也有明确边界

`assistant_runtime.py` 已实现多轮工具调用、会话状态、证据、流式输出、调用记录、取消检查和最大 10 轮限制；还能拦截同一会话中相同签名的重复工具调用。这些是可以保留的工程资产。[E10]

默认工具主要为 7 个读取型接口：`get_log_context`、`search_mods`、`get_active_mod_list`、`get_mod_info`、`get_mod_rules`、`get_mod_user_data`、`get_group_mods`。其中 `get_mod_user_data` 读取的是管理器的别名、标签、备注、分组等，**不是任意游戏存档或模组配置编辑器**。[E09、W09]

游戏日志助手默认提供 `MOD_STATE` 和 `MOD_RULE` 动作；前端卡片将启停请求传给列表 store、将规则请求交给规则系统。代码中的列表启停是对活动/非活动列表的调整，不构成 Probably Stolen 所需的多文件安全部署，也没有因为显示成功通知就完成游戏内验证。[E10、E11、W10]

因此值得复用的是“读取上下文—有证据的建议—可解释动作卡片”的体验。需要新增的是“计划校验—备份—文件事务—重新启动—验证—失败回滚”的执行内核。

## 五、为什么不能把 RimCrow 原样改名

### 5.1 About.xml 和 ModsConfig.xml 是领域边界

原扫描器把没有 About.xml、又不是 DLC 的目录视为无效；原加载列表管理器以 ModsConfig.xml 为核心。Probably Stolen 的 DLL 元数据、资源包、同名程序集筛选、Mods/Plugins/UserLibs 阶段与这些假设不同。[E08]

RimCrow 的“保存列表”主要更新一个游戏配置文件，而本项目的“应用配置”可能需要变更多个 DLL、资源文件及共享配置。原来的原子 XML 写入可以借鉴，但不能当作多文件事务已经实现。

### 5.2 四种顺序必须分开

| 顺序 | 是否能从管理器 UI 随意改变 |
|---|---|
| 界面显示和用户分组顺序 | 可以 |
| 加载器发现、筛选程序集的过程 | 受该版本加载器规则约束 |
| Melon 注册/回调优先级 | 受依赖处理和 MelonPriority 等规则约束 |
| Harmony 补丁实际执行顺序 | 受补丁 priority、before/after、类型及运行时注册等影响 |

v0.7.3 的 `MelonBase.SortMelons` 调用依赖拓扑处理后，再按 Priority 排序。Harmony 官方文档也明确说明补丁顺序不是简单线性的，最后加载的模组可以包含先执行的补丁。[W04、W06]

上传样本 `KitchenCrashTrace.dll` 与 `XIAOWOTradePerks.dll` 都声明了 `MelonPriority(-2147483648)`。简单给文件名前加 `01_`、`02_`，并不能可靠重排这些机制；还可能破坏 ItemForge 的文件名前缀发现及其他模组的约定。[E04、E05]

第一版应把 RimCrow 的“自动排序”转化为 **“依赖和兼容性检查”**。不能实现的排序规则要明确标成“建议/未执行”，而不是写进管理器数据库后告诉玩家已解决。

### 5.3 子文件夹语义也必须按版本实现

官方 v0.7.3 支持带 manifest 条件的子目录扫描，并有禁用子目录或取消 manifest 要求的选项；默认排除规则还包含准确大小写的 `Disabled`、`Broken`、`Retired` 等目录名。[W05]

因此既不能说“只扫描 Mods 根目录”，也不能说“所有子目录都会加载”。更不能凭经验认为放进 `Mods/disabled` 就一定安全。**管理器停用库应放在整个游戏加载扫描树之外**，以免受到版本、配置和二次框架扫描差异影响。

### 5.4 日志监视器需改造，不只改路径

现有 `_tail_log_file` 面向其自己的实时 JSON 行日志，只持续读取已打开文件；该函数中未见文件截断/替换检测，对无法解析成 JSON 的行直接跳过。[E12、W11]

MelonLoader 的彩色转储/纯文本日志、自定义模组日志、Player.log 与这个格式不同。新 tailer 必须支持文件迟到创建、轮转、截断、分段写入、多字节字符跨块、独立读取偏移、界面关闭后继续或停止的明确生命周期。

### 5.5 扩大 Agent 权限之前，先补执行时鉴权

当前会话先筛选提供给模型的工具 schema；但 `_execute_tool_calls` 会把返回的名称交给 `execute_structured`，后者查完整工具注册表。该执行路径中没有再次按本会话允许工具集合做显式拒绝。[E09、E10]

这是**扩展时需要先修复的权限边界缺口**，不应夸大成现成任意文件写入漏洞：当前注册工具本来主要是只读。但一旦添加下载、文件移动、配置写入或修复动作，仅靠“没有把工具告诉模型”就不能成为权限控制。

应使用后端校验的 capability/allowlist，并把读取范围、配置代次、动作风险、批准记录一起绑定。前端按钮确认和 Pydantic 参数合法性都不能替代执行授权。

## 六、推荐的产品范围与信息模型

### 6.1 第一版必须完成的实际功能

| 领域 | 第一版应具备的能力 | 暂不承诺 |
|---|---|---|
| 游戏发现 | Steam 库 + 手动选择，校验 EXE、Data、IL2CPP 和加载器 | 从目录名猜所有安装信息 |
| 接管现有 Mods | 零改动扫描、快照、身份识别、未管理文件提示 | 第一次打开就重命名或整理所有文件 |
| 安装管理 | DLL/ZIP 导入预览、文件清单、启停、版本选择、可撤销移除 | 自动执行压缩包里的安装脚本 |
| 内容依赖 | MelonInfo + 静态资源识别 + 已知框架规则 + 人工补充 | 仅 AssemblyRef 就识别全部兼容性 |
| 多配置 | 组合、版本锁、配置快照、部署历史 | 同一游戏目录同时运行两种物理部署 |
| 运行观察 | 本次加载状态、被覆盖、自停用、相关日志、上次可用配置 | 启动进程存在就等于全部玩法正常 |
| AI | 证据解释、受控修复计划、执行与验证结果回报 | 任意 DLL 自动热修复 |

本地文件来源必须优先；没有必要为了仿照 RimCrow，把 Steam 创意工坊、SteamCMD、Nexus 或 Thunderstore 的整套功能都先移植。此次没有取得 Probably Stolen 已具备相应公共模组仓库的充分证据，应在真实数据源确认之后再接入。

### 6.2 核心模型

建议最少建立以下对象：

- **GameInstallation / RuntimeFingerprint**：安装路径、游戏渠道、AppID、buildid、EXE/关键元数据指纹、Unity、IL2CPP、Loader/Runtime 信息。
- **ModPackage / ModRelease / Artifact / FileOwnership**：逻辑模组、发布版本、不可变文件、安装目标和归属；支持一个包多个 DLL、资源与配置模板，也支持资源包没有 MelonInfo。
- **Profile / DeploymentGeneration**：玩家想使用的组合，以及已实际部署的版本；二者不能混成一个列表。
- **RuntimeSession / Observation / DiagnosticEvidence**：本次运行实际看到了什么，证据来自哪个日志、哪个时间、哪个哈希。
- **ActionPlan / Transaction / Backup**：准备改什么、前置条件、批准记录、执行进度与如何恢复。

状态应同时表达三个层次：**期望状态、磁盘部署状态、运行观测状态**。例如一个模组可以“期望启用、文件已部署、运行时自停用”；不能只用一个绿色开关掩盖最后一项。

依赖关系也应有类型与来源：硬依赖、软依赖、替代/互斥、加载优先建议、同程序集遮蔽、文件冲突、内容 ID 冲突。未经作者声明或实测验证的关系必须标记为推断。

### 6.3 管理器清单示意

下面是**建议新增的管理器私有清单结构**，不是 MelonLoader 原生 manifest，也不是现有模组官方格式：

```json
{
  "schemaVersion": 1,
  "packageId": "local.assigned-id",
  "displayName": "从作者清单或元数据读取",
  "releaseVersion": "保留原始版本字符串",
  "kind": "melon-mod",
  "artifacts": [
    {
      "fileName": "OriginalName.dll",
      "destination": "Mods/OriginalName.dll",
      "sha256": "导入时计算的完整哈希",
      "role": "entry-assembly"
    }
  ],
  "dependencies": [],
  "compatibility": {
    "gameBuilds": [],
    "verification": "unknown"
  },
  "configOwnership": [],
  "source": {"kind": "local-import", "trust": "user-provided"}
}
```

已有裸 DLL 不应因没有此清单而拒绝管理。系统可以生成本地清单，但必须区分“作者声明”与“管理器推断”，不能擅自捏造来源、许可证或最低游戏版本。

## 七、推荐架构与源码改造点

                    │
          窄接口的应用服务与命令层
                    │
     ┌──────────────┼──────────────┐
     │              │              │

保留三个小边界即可：游戏适配器负责安装识别/日志/存档探测；加载器适配器负责扫描阶段、版本规则、环境要求；内容框架适配器补充二次包和逻辑依赖。不要把单游戏需求演变成大量插件接口。

## 八、文件部署和回滚：稳定性的核心

### 8.1 首次接管必须零破坏

首次扫描仅建立索引和快照，不重命名、不移动、不删除。将原始组合保存为“导入时配置”，记录未托管文件。资源目录无法明确归属时展示候选关联，不能按文件名前缀武断认领整个目录。

包仓库应位于游戏扫描树之外，并使用内容哈希存放不可变原件。游戏目录只是部署目标；每次部署生成完整 manifest。MVP 优先普通复制，避免硬链接把游戏中的意外修改反向污染原始包仓库；符号链接/目录联接也需要额外权限和路径安全处理，不应作为首版稳定性的前提。

### 8.2 一次启停可能是多文件变更

`Mods/BrewingExpansion`、`Mods/MoreStorageColors/Textures`、`UserData` 的各类配置、`Mods/item_catalog.json` 等已说明资产不是只有 DLL。[E07]

正确做法是生成文件级差异：新增、替换、移除、保留、冲突。只移除由当前已管理包拥有且无需共享的文件；不清空整个 Mods；不清空 UserData；不自动删除其他模组或玩家手动放入的文件。

### 8.3 事务协议

建议状态机：

```text
Planned → Staged → Validated → Applying → Committed → Verified
                              │             │
                              └─ Recover / RollbackRequired ─┘
```

事务中应包含：游戏进程检查与单实例部署锁、路径约束、空间检查、旧文件快照、暂存文件哈希、持久化 journal、每一步前后哈希和动作结果。新文件完整写入同卷临时位置后，再做单文件替换。

**不能宣称多个 DLL 加一个配置文件天然原子提交。** `os.replace` 只能提供对应文件操作的原子性，整个部署集合需要 journal 和恢复流程。断电后下次启动应先识别未完成事务，在用户通过管理器启动游戏前恢复一致状态。用户绕过管理器直接从 Steam 启动是现实边界，无法仅靠 UI 锁完全禁止；应尽量缩短变更窗口并清楚报告未完成部署。

回滚也需要当前文件前置哈希：期间出现用户外部修改时，先保全变更并进入冲突处理，而不是把回滚当作覆盖一切的许可。

### 8.4 配置与存档分别处理

`.cfg` 并不必然是 INI。该样本存在 TOML 风格共享配置，且同一配置可能混合界面选项和持久进度标记。应按实际格式解析，保留注释、未知字段和格式；优先做字段级修改与冲突检查，不整体重写未知配置。

某些模组内部提示要求退出游戏再修改配置；游戏运行中也可能回写值。因此默认禁止运行中替换 DLL 或写共享配置，界面显示“待下次启动应用”，不要制造热生效幻觉。[E05、E07]

Unity 文档给出 Windows 的通用 persistentDataPath 规则，但本样本没有完整玩家存档目录。可根据 `app.info` 的公司/产品名提出候选路径，再现场校验；不能把推测路径当成已经确认的存档位置。[E02、W12]

“克隆管理器配置”只克隆组合和配置，不自动隔离游戏存档。安全测试至少要确认实际存档路径、备份范围及 Steam Cloud 状态，并使用可丢弃测试存档。没有验证隔离机制前，不提供“无人值守批量打开正式存档排障”。

### 8.5 自动更新应该是受控升级，而不是自动覆盖

记录模组版本和哈希锁；检查更新可自动，下载可缓存，应用更新要在游戏停止后按兼容策略执行。内容类和破坏存档兼容的升级应单独确认，先在测试配置中验证。应用自身升级也要有独立的版本来源、校验、备份和数据库迁移恢复。

哈希只证明字节一致性，不证明作者可信。源站、签名、作者身份、资产许可证要分开记录。不要将来源不明的 Git 仓库构建脚本当成可安全自动运行的安装器。

## 九、AI Agent 设计：立即采取行动，但不盲目改动

### 9.1 先规则、后 AI；基础管理无需 AI 在线

本次已经发现的 45→43、同名遮蔽、内容包识别、历史 .NET 恢复、自停用文案、委托主模组等问题，大多可以用本地确定性规则识别。AI 更适合跨日志关联、解释、提出最小试验方案和整理报告。

推荐顺序：**本地扫描 → 确定性规则 → 证据索引 → AI 补充判断 → 后端批准/执行 → 新运行验证。** 模型断网、限流、密钥失效时，安装、启停、备份、启动和基本诊断必须仍然可用。

没有必要首版就引入多个互相对话的 LLM Agent。一个有证据工具的诊断规划器，加确定性的执行器、验证器，通常更容易控制成本和故障范围。

### 9.2 推荐新增的工具边界

读取工具可以覆盖：运行环境、文件元数据、逻辑依赖、最近运行状态、指定日志片段、指定配置 schema 与脱敏值、部署差异、最近成功配置。返回结果附带 `evidence_id`、会话、原始文件和行范围、时间、相关哈希与置信级别。

模型只提交 `ActionPlan`。后端执行器负责受控的：创建备份、建立测试配置、选择互斥版本、隔离已确认旧组件、变更允许字段、应用已验证包、启动指定配置、收集新日志及回滚。

默认不提供任意 shell、PowerShell、任意目录写入、执行下载脚本、修改 GameAssembly、任意 DLL 二进制 patch 或删除存档。真正需要开发者改源码的场景应另设隔离工作区：有授权源码、明确 diff、编译和测试，再经批准将构建产物导入管理器；不能和玩家一键排障权限混用。

### 9.3 修复计划的数据契约

```text
plan_id
profile_id + expected_deployment_generation
game_fingerprint + loader_version
reason + evidence_ids
preconditions（进程已退出、目标文件原哈希、允许的路径范围）
operations（严格白名单，不含任意脚本）
backup_scope + estimated_disk_requirement
risk_level + approval_scope
restart_required
verification_checks
rollback_operations
```

执行前重新验证全部前置条件。模型分析后用户又换过 DLL，旧计划必须失效重新生成，不能拿过期证据修改新环境。操作要有幂等键、阶段进度、取消语义和最多重试次数，不能无限“修复—启动—失败—再修复”。

### 9.4 自动化分级

| 风险 | 推荐默认策略 |
|---|---|
| 本地读取、扫描、脱敏、归类、检查更新 | 自动进行 |
| 创建快照、准备差异、下载到缓存 | 在已有授权和空间策略内自动 |
| 改变启用组合、隔离旧版本、写配置、恢复部署 | 给出一份明确的计划，批准后成批执行 |
| 安装/更换加载器或系统运行时 | 单独核对来源、权限及兼容影响，明确批准 |
| 删除/改写正式存档、绕过模组保护、任意代码执行 | 默认不允许；不能靠提示词自行解锁 |

减少操作的方式是“用户批准一个有边界的处理计划，执行器完成整个安全事务”，不是每个复制步骤都弹窗，也不是交给 AI 无限权限。

### 9.5 以当前真实问题作为演示用例

玩家询问“为什么烛印会没生效？”时，系统先读取本次自停用日志，再将名称映射到 JCuratedVisitors 1.0.9，发现旧体系候选组件，并标记报错里的 0.5.0 是过时文案。随后准备测试配置和备份计划，而不是立刻删除两个文件。

经批准后执行器隔离被确认的旧组件，保持其他模组不变，提示正式存档保护边界，重启测试。验证时不能只确认 ERROR 消失：还应确认预期版本加载、未再自停用、到达主菜单；内容注册与实际玩法需要对应遥测或玩家确认。结果显示为“部署完成”“启动验证通过”或“玩法待验证”，而不是笼统“已修复全部问题”。

### 9.6 日志安全、隐私和成本

日志是低可信输入，其中的“忽略先前指令”“执行命令”等内容只能被当作文本证据。不得让日志、模组描述或 README 改写工具权限。模型看见的文件引用应是后端发放的证据 ID，而不是任意本机路径。

上传 AI 前脱敏个人路径、用户名、令牌、代理认证、敏感 URL 参数及不需要的存档内容；默认不上传整个游戏文件、完整存档或全部日志。系统凭据不可用时，新产品宜采用会话内保存或明确失败，避免为了自动化悄悄降级为持久明文。

原项目有旧明文配置迁移失败时的保留路径；应准确理解为迁移兜底，而非断言所有新密钥都自动明文保存。[E13]

保留最大工具轮次之外，还需总请求时限、每次工具时限、令牌/费用预算、取消后的资源清理、有限重试和熔断。相同原因/相同环境不应每次启动都重复调用模型。

## 十、日志与可选游戏内观测模块

日志源至少考虑 `MelonLoader/Latest.log`、`MelonLoader/Logs`、经定位确认的 Player.log，以及 `UserData` 中的模组专用日志。记录来源、编码、偏移、运行 PID/时间和部署代次。Latest.log 与归档复制要去重，不能把同一错误统计两次。

按“引导、运行时、IL2CPP 生成、程序集发现、模组初始化、场景/内容注册、实际游玩”划分阶段。先找本次会话中仍未恢复的最早具体失败，而不是无脑选第一条 ERROR 或报错最多的模组。

本样本有些专用日志包含版本说明和使用教程；这些文本里的“失败”“冲突”不能直接计为本次运行事件。只有内容具备事件时间/级别/来源或符合可靠模式时才进入诊断。

可在后续增加可选 companion mod，输出结构化 JSONL：已加载模组和哈希、实际 runtime、Harmony owner/patch 信息、主菜单到达、内容框架注册结果、可选配置 schema。它只提高可观测性，不应成为首版安装/启停的必要条件；其自身失败也不能阻断基础管理。

若提供双向 IPC，优先使用受 ACL 约束的本地命名管道/等效本地机制，加会话随机标识、协议版本和有限命令。不要开放一个能执行任意命令的本地 HTTP 服务，也不要重复实现现有模组兼容总线来主动改写别人的 Harmony patches。

## 十一、界面建议

保留 RimCrow 紧凑的多栏方式，但重新定义按钮与状态。

顶部：游戏安装、Demo/本体渠道、版本/构建、配置选择、环境健康。  
左侧：选中模组详情、版本/作者、文件组成、来源、依赖、兼容性和最近运行证据。  
中间：可用库与当前配置；支持搜索、多选、分组、拖拽组织，显示“已部署/待应用/已加载/内容包已注册/被覆盖/自停用/未知”。  
右侧：问题、AI、变更计划、备份和运行历史。  
底部：扫描、检查兼容性、查看待应用变更、应用并启动。

建议默认只突出确实需要用户决策的问题。信息级兼容提示折叠，潜在风险以非阻断方式显示；只有缺失硬依赖、文件写冲突、未完成事务、明确不兼容等阻断条件才禁用启动或要求确认。

“撤销列表编辑”和“回滚已部署版本”必须是两个不同操作；“备份管理器组合”和“备份游戏存档”也必须分开。不要用同一个“保存成功”通知覆盖这些语义。

## 十二、自动化与健壮性验收矩阵

| 场景 | 必须达到的结果 |
|---|---|
| 首次接管当前样本 | 原游戏文件不变，45 个 DLL 可识别并解释 43 个直接加载项 |
| 没有 MelonInfo 的资源包 | 不误报损坏；提供所属框架和内容注册证据 |
| 同名程序集不同文件 | 提示高版本遮蔽，保留原件，不自动误删 |
| 中文、空格、百分号与大小写差异 | 路径不损坏；Windows 目标路径按适当规则检测冲突 |
| ZIP 路径穿越、绝对路径、链接和目录联接 | 拒绝越界；检查解包后规范路径和重解析点 |
| ZIP 炸弹、超大/畸形 DLL | 总大小/文件数/超时限制，扫描进程故障不影响主 UI |
| 安装到一半被终止、断电、磁盘满 | 原件保全，有 journal；重启后可恢复一致部署 |
| 游戏运行时点击应用 | 阻止替换已加载文件，只允许准备计划 |
| 杀毒占用、权限不足 | 有限重试，明确错误，不通过强制关闭安全软件兜底 |
| 外部手动换 DLL | 识别环境漂移，旧计划失效，要求重新评估 |
| 多文件包共享资源 | 不因停用一个包删除另一个包使用的文件 |
| 日志轮转、截断、半行写入 | 不漏会话、不重复、不把原始非 JSON 行丢弃 |
| .NET 初始化失败后恢复 | 标记已恢复，不继续当成当前阻断错误 |
| 旧版文案与元数据冲突 | 显示证据冲突，不按旧字符串自动降级 |
| AI 限流/断网/取消 | 基础管理可用，有限重试，任务最终结束 |
| 模型调用未授权工具 | 后端拒绝，即使工具已注册也不能绕过会话权限 |
| 日志中注入命令 | 作为普通文本保留，不扩权、不执行 |
| 配置包含未知字段/进度标记 | 字段级更新保留未知数据，不使用一键清空 |
| 正式存档或 Steam Cloud 未隔离 | 不执行无人值守破坏性试验，清楚说明未验证边界 |
| UI 显示“已修复” | 必须有对应新会话验证；否则只能写“已应用/待验证” |

以上为建议验收条件，不是已经实现或已经通过的项目测试。建议用本次发现构建去敏的回归用例；公开仓库使用自制最小 DLL/日志 fixture，不直接上传整个游戏和未经许可的模组二进制。

## 十三、开发阶段与优先级

**阶段 0：建立能开发和验证的独立基线。** 固定上传提交，恢复 Windows 开发/打包环境，运行原测试并记录基线。分离应用名称、数据目录、keyring service、数据库和自动更新地址；去掉或关闭全部 RimWorld 专属在线拉取与界面入口。验收是新应用不会误操作原 RimCrow 或原游戏配置。

**阶段 1：只读扫描与现实模型。** 实现游戏识别、45 个 DLL 元数据扫描、包/文件归属、内容包识别、同名程序集规则、多源日志及三层状态。此阶段就能产生很有价值的诊断界面，不必等待 AI。

**阶段 2：安全部署和多配置。** 实现导入、预览、包仓库、锁、journal、备份/恢复、版本选择与启动守卫。先做到没有 AI 时也能可靠管理现有组合，再接入自动修复。

**阶段 3：有执行闭环的 AI。** 复用会话/卡片，新增只读证据工具和 ActionPlan，接入后台权限、执行、验证与回滚。以本报告的自停用、版本遮蔽、历史恢复为回归案例。

**阶段 4：增强与分发。** 在实际需要时接入可信在线源、作者清单和可选 companion，完善配置编辑、升级迁移、性能与崩溃诊断，发布小范围测试版本。

不建议在第一轮同时做创意工坊平台、通用模组市场、可执行代码 Agent、跨平台全部支持、存档自动迁移和任意 Harmony 顺序编辑。优先把 Windows 单游戏、现有 Mods 组合、可回滚部署做可靠。

排期时应分别估算 UI 适配、领域模型、事务、日志、AI、Windows 质量验证，不能把“改了多少文件”当作剩余工作的线性比例。项目当前最大的工作量不是替换游戏名，而是把文件修改和验证做成可靠产品。

## 十四、许可、发布与最终建议

RimCrow 的 MIT 许可证允许修改和分发，但要求保留版权和许可声明。应明确产品是独立衍生项目，不冒充原项目官方发行版。[E15、W13]

游戏文件、生成的 IL2CPP 程序集、第三方模组、图片和其他依赖分别受各自条件约束。管理器发行包优先只包含自身代码和获许可依赖；让用户选择本机合法安装，从官方来源按需获取加载器或运行时，避免把上传游戏包当成可公开再分发的安装资源。

**最终建议：采用裁剪式 fork，保留 RimCrow 的交互工作流和 AI 会话资产；将新项目的核心定义为“模组身份、可复现部署、运行证据和可回滚修复”，而不是 RimWorld 加载顺序编辑器的换皮版。**

第一项最有辨识度的验收应当是：面对当前这个包含 45 个 DLL 的真实环境，管理器能够正确解释为什么只有 43 个直接加载项、识别资源包与高版本遮蔽、指出真正的自停用问题，并在不误删其他模组、不伤害正式存档的条件下提供可验证处理方案。
