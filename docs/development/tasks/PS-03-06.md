## 实现步骤

1. 使用已选安装的 EXE/工作目录和必要参数直接启动，不拼 shell、不照搬其他游戏存档参数。
2. 复用当前后端入口与普通进程检查，运行失败、缺文件、权限问题给出清晰提示。
3. 已有诊断日志可作为可选信息展示，不要求先实现历史会话、主菜单、内容和玩法检查。
4. 合成进程验证成功/失败和路径参数；真实游戏只有获得对应启动授权时才测试。

启动只接受 `installation_id`。后端从已登记安装取得绝对 EXE/工作目录，不接受 shell、参数、环境或工作目录。新进程在恢复主线程前核对实际映射映像，使用已有检查；拒绝时只结束本次未运行的子进程。状态用实际进程句柄观察；退出码是进程结果，不是玩法验证。

## 验收标准

1. 在合成安装中，实际启动预期测试进程；中文、空格等路径有效，非法安装不能启动任意命令。
2. 未启动、启动失败和已启动显示真实区别；不把旧日志或进程存在当作游戏运行正常。
3. CASE-036 仅普通启动与错误处理为本卡最低范围；真实玩法、会话诊断为可选记录，不前置安装管理。

## 验证内容与命令

- 本卡创建 `tests/integration/test_launch_verification.py`，使用自制进程验证指定路径启动、退出和普通错误。
- 实际按钮接入时用现有桌面 harness 验证；真实游戏启动保持独立可选范围。
- `tests/desktop/test_game_launch.py` 使用真实 WebView/Vue/bridge 和自制进程，以自动 DOM 事件检查双击、状态、退出后再启动、错误和管理器重开。不是人工或可信指针验收。

适用 Profile：synthetic、desktop-local。先用本卡实际创建的直接入口：

```powershell
.\.venv\Scripts\python.exe -m pytest tests/integration/test_launch_verification.py -q
```

desktop-local 直接入口需已有前端构建；将下面的 `<UTC-run>` 替换为新的本任务证据目录，harness 拒绝越界目录：

```powershell
.\.venv\Scripts\python.exe -B -m pytest tests/desktop/test_game_launch.py -q --basetemp "docs/development/evidence/PS-03-06/<UTC-run>/desktop-tmp"
node --test frontend/src/features/installations/gameLaunchRuntime.test.js frontend/src/app/bridge/client.test.js
```

仅当前 runner 已映射时选择相应路线：

```powershell

pwsh -NoProfile -File scripts/verify.ps1 -Task PS-03-06 -Profile desktop-local
```
