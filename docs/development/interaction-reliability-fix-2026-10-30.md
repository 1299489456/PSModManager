# 0.3.1 操作连贯性修复

## 本轮结果要求

用户在管理器完成模组选择、保存和启动，进入游戏后直接游玩，无需再进入游戏的模组菜单。启用不新增权限弹窗；权限和风险证据留在详情。高风险、隔离和分析未完成仍须给出真实阻断原因。

本轮明确替代旧方案中“批准只能由游戏完成”的限制：显式保存可以按当前游戏协议写入用户选定内容的批准，不能修改游戏 DLL 或关闭游戏检查。

## 五个问题的修复

| 问题 | 根因 | 现在的行为 |
| --- | --- | --- |
| 后台工坊探测抢占，保存需重试 | 只读 Steam 探测在 IPC 等待期间占用安装互斥锁 | 前台操作取消并等待自己的只读探测退出，再取得写锁；实际下载、未确认操作或其他写入不冒充可取消探测 |
| 保存成功残留旧错误 | 无变化时跳过保存，旧错误未清理；保存后未等待启动结果 | 无变化也执行当前内容检查；开始重试及成功后清理旧错误；单击依次检查、保存、等待启动结果，不再弹第二个确认框 |
| 保存后仍需游戏内批准 | 之前仅写启用列表，未写当前内容批准 | 显式保存完成静态检查、游戏原生检查、批准与顺序的原子写入；不新增权限弹窗 |
| 工坊显示已连接又要求重连，筛选慢 | 公共目录过期被混作 SDK 会话失效，冷查询同步等待 HTTP | 目录和账号状态分开；缓存或加载态立即返回，后台完成后更新；快速切换不让旧响应覆盖当前筛选 |
| 游戏运行但顶栏显示退出 | 顶栏退出后停止轮询，页面各自维护状态 | 运行时每 2 秒、空闲/退出/未知时每 5 秒持续核对；顶栏与模组工作区共用进程观察，写前另做实时检查 |

模组页在后台只读探测期间仍允许发起前台保存。该准入仅适用于已证明持锁者是本管理器探测、游戏已退出且唯一阻碍是该锁的情形；未知进程、恢复任务和其他持锁者仍阻止写入。

## 保存即完成当前内容批准

1. 对目标启用包取得完整内容指纹。复用与内容、规则和扫描器一致的完整报告；未检查、已更新或上次未完成的内容重新检查。
2. 在现有 LPAC 隔离进程中调用当前安装的游戏原生 `ModScanner.Scan`。只加载固定游戏扫描依赖；候选 Mod 由 DseCecil 读取元数据，不作为程序集执行。
3. 高风险、隔离、扫描缺失、游戏原生拒绝或检测到未声明权限时，显示证据并停止本次保存/启动。原生证据新增到详情的“安全”页，不把体积大或单独联网当作恶意结论。
4. 检查成功后再取得写锁，复核版本、来源、完整内容及游戏原生指纹。创建恢复点，合并写入启用顺序和 `modTrust`，再回读核对。保留无关游戏设置和未知字段，`developerMode` 保持关闭。
5. “保存并启动”等待保存结束后再请求启动；受控启动再次检查内容。保存、批准和实际运行记录仍是不同事实。

长只读内容检查不再每 256 KB 重复查询进程、数据库和恢复状态，改为最长每 0.5 秒复查；全量哈希不变，每包前后及写入边界仍即时检查。17.6 MB 隔离资源包使用生产守卫的同次完整读取：状态查询开销从 1.250 秒降到 0.155 秒，持锁查询从 1.056 秒降到 0.052 秒；这是内容读取阶段的测量，不是完整扫描/保存耗时。

协议依据是本机 Steam build **26284217** 的 `ModLoader`、`ModScanner`、`ModTrust` 和 `ModFingerprint`。批准绑定 ID、Local/Workshop 来源、Workshop ID、清单和声明 DLL 顺序/内容；使用独立 .NET 惰性协议测试核对输出的 `Match`，没有修改游戏 DLL。

游戏自带的停用/封禁策略、原生扫描拒绝和模组自身初始化失败仍会影响加载。管理器不会为绕过这些结果开启开发者模式或伪造“正在运行”。恢复处置只恢复禁用内容，不自动重新批准。

## 工坊切换不再等网络完成

公共目录独立后台队列、请求合并与最后选择优先；账号 SDK 状态不被公共网页超时覆盖。目录更新失败仍显示对应错误和已有内容，但不因此关闭可用的订阅功能。

真实公共目录读取对比（本机一次测量，非性能保证）：

| 查询 | 原同步返回 | 新冷查询返回加载态 | 实际网络完成 | 已缓存查询返回 |
| --- | ---: | ---: | ---: | ---: |
| 最热门 | 2.640 秒 | 2.3 毫秒 | 2.576 秒 | 1.3 毫秒 |
| 最近更新 | 1.141 秒 | 0.1 毫秒 | 1.906 秒 | 1.3 毫秒 |

这项改动消除的是界面等待网络的阻塞，不把网络读取时间说成毫秒级。真实 WebView2 的受控慢网络验收中，冷筛选切换可见为 5.1 毫秒，返回缓存页为 89.9 毫秒。

## 现有数据处理

本轮五项问题均找到当前代码原因，已检查的工坊版本 1 缓存仍是合法数据，因此没有清空用户数据目录。旧版本只保存顺序、缺少批准的配置，在下一次显式保存时按新流程检查并补齐。损坏或旧规则缓存不作为安全依据；检查未完成的缓存重新读取，而不是继续复用失败结果。

真实游戏程序集和安装状态只读调查；所有写入、批准、进程启动测试使用隔离数据与自制惰性样本。不运行真实 Mod，不变更用户 Steam 订阅。对确有证据的旧逻辑数据先备份再迁移，正常用户设置、配置和恢复材料不做整库清空。

本地候选目录：`.preview/interaction-fix-portable-20261030-01`。冻结包检查包括真正从冻结 EXE 加载产品模块执行上述闭环、冷/热工坊目录响应，以及全新与隔离旧数据启动。只有通过后才更新 `docs/development/current-local-delivery.json`，其中记录实际产物和验收文件位置。

未执行真实游戏和真实 Mod 的加载游玩，也未对真实 Steam 账号订阅/取消订阅。实际游戏菜单免操作效果仍需使用新包启动后观察；当前证据是原生协议、真实扫描器、生产 API 和 WebView2 的隔离闭环。首轮未缓存分析需要时间，界面显示检查阶段且不锁住其他页面；不可用分析不能跳过后放行。本轮不提交、不推送、不发布。
