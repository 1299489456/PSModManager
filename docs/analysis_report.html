0. 结论与阅读说明

可以改，而且值得利用 RimCrow 已有的 UI、交互、任务反馈、日志工作台和 AI 会话框架。但不能把它当成“换游戏名称、把扫描路径改成 Mods”这样的小改造。RimCrow 的核心管理对象是 RimWorld 模组目录与 XML 载入列表；本游戏的实际对象是 Melon 模组、二级运行时内容包、共享配置、资源文件及运行期兼容状态。

推荐的产品定位是：面向 Probably Stolen 的可恢复部署管理器，并附带有证据、受控执行的 AI 诊断助手。 先把包识别、部署、备份、回滚和状态核验做可靠，再让 AI 调用这些能力。不要让 AI 替代底层规则、文件事务或兼容性事实。

本报告区分三种内容：已在上传文件中观察到的事实、由事实推导的风险、建议实现的目标设计。后两者不是现有软件已经具备的功能。

检查范围与限制

已解包两个归档；检查游戏目录、两个 MelonLoader 日志文件及代表性模组日志；对 Mods 根目录全部 45 个 DLL 进行只读 PE/CLI 元数据、程序集引用、相关属性和嵌入 JSON 检查；审阅 RimCrow 关键后端、前端、AI、配置、包安装和浏览器桥接源码。未对全仓每一行代码逐行审计。

未在 Windows 上启动游戏、执行模组 DLL、运行桌面 GUI、完成项目完整构建，或实测存档隔离。不能据此声称所有模组兼容、AI 能成功修复、或改造后的程序已经可用。本文交付的是分析和实施方案，不是已改造的可执行程序。

本地来源采用证据编号：G1–G8 为游戏文件，R1–R18 为 RimCrow 源码，T1 为实际检查。具体相对路径、原始行号、SHA-256 和摘录见 evidence_appendix.md。全部 DLL 元数据见 mod_inventory.json。公开技术与许可来源见文末 O1–O5。

2. 现有游戏包已经暴露出的关键设计要求

2.1 合法内容包不一定是一个 Melon 模组

PSItemPack_SanmuShiwushechipinPack1.dll 没有 MelonInfo 属性，但包含 ItemForge.items.json 与图标等 22 个嵌入资源。JSON 声明 BundleId 为 sanmu_shiwushechipin_pack1、名称为“食物奢侈品拓展包”、RequiredRuntimeApi 为 5，并含 21 个物品。主日志 L555 明确记录 ItemForgeRuntime 读入了它的 21 个配置。[G2、G5]

因此，以下实现会误伤正常模组：只显示带 MelonInfo 的 DLL；把无 MelonInfo 的 DLL 一律挪到 UserLibs；按 43 个 loader 注册项推断剩余文件无效；只移动主 DLL 而忽略所属内容组件。

扫描层至少应识别 MelonMod、MelonPlugin、ItemForge 内容组件、CharacterForge 内容组件、依赖库、资源文件和暂无法分类文件。一个发行包可以包含多种组件；一个 DLL 也可能同时具有 Melon 入口与嵌入式内容清单，不能把这些类型设计为绝对互斥。

2.2 依赖版本不只有“Mod 版本号”

实际嵌入清单中，gofishing 要求 ItemForge Runtime API 19；MoreFood 要求 API 12；三木内容包要求 API 5；钓鱼商人要求 CharacterForge Runtime API 1。本次运行日志报告 ItemForgeRuntime 为 API 19、CharacterForgeRuntime 为 API 1。[G2、G5]

需要分别存储：显示版本、程序集版本、生成器版本、运行时 API 要求、游戏适用版本、加载器约束。不能拿 ItemForgeRuntime 1.2.3 与 RequiredRuntimeApi 19 做版本字符串比较。

当前快照还包含钓鱼料理扩展的调试物品嵌入清单。能静态提取清单不等于这些内容在本次游戏中都注册生效。实际加载情况必须由对应运行时日志或探针确认。

仅靠 AssemblyRef 也不够。当前多个模组的前置检查和协作出现在日志里，但不表现为直接跨模组程序集引用；反射和字符串标识会使纯引用图漏掉依赖。依赖证据应有来源和可信度，不明关系保留为“待确认”。

2.3 旧版组件共存导致明确自停用，但修复还涉及存档

主日志 L1016 明确表示“本次运行已停用本 MOD”，原因是检测到旧版两个 DLL，并要求退出、移走旧版、使用新存档，其他作者模组保持原样。目录中同时存在 JCuratedVisitors.dll、PSItemPack_CuratedVisitors.dll、PSCharacterPack_CuratedVisitors.dll；后两者元数据均显示 0.3.3。[G3、G4、G5]

这是 AI 可以给出高价值建议的真实案例。但报告不能仅凭名字相似就授权删除两个文件。应先确定用户想保留的内容版本，关联对应哈希、清单和作者迁移说明，然后生成只影响该组合的停用计划。

还有版本来源不一致：JCuratedVisitors 的 MelonInfo/程序集版本指向 1.0.9，而诊断文字称 0.5.0。两者都应原样记录并标注来源，不能由 AI 把文本中的数字当成唯一真实版本。

“使用新存档”不能被包装成无风险自动修复。管理器应展示存档影响，禁止自动覆盖旧存档。文件恢复成功不等于旧存档恢复兼容。

2.4 主动兼容停用不应被判为损坏

XIAOWO-PrecisionBayExpansion 在检测到 XIAOWO-TradePerks 后记录 INACTIVE，并说明功能交由主模组控制。之后还有相应主菜单标题显示日志。[G3]

合理显示是“兼容模式：由主模组接管”，而不是“加载失败，建议重装”。运行状态应包含：尚未验证、已注册、已初始化、主动兼容停用、前置不满足自停用、初始化异常等。无法观察到初始化结果时保持未知，而非把 loader 注册成功等同全部功能正常。

2.5 潜在 Harmony 冲突不是 21 个已确认冲突

本次 XIAOWO-TradePerks 自报：共享方法 46、潜在冲突 21、确认冲突 0、停用模块 0，并称已去重 62 个补丁。[G3，L1026–1027]

这些是某模组针对该次运行的诊断指标，不是管理器已经独立证明的全局结论。管理器可以展示来源和方法关联，不应自动禁用全部相关模组，也不应自行再运行一次全局补丁去重。

多个补丁作用于同一方法、Prefix 可能跳过原方法、Postfix 修改返回值，都只能构成进一步调查线索。优先级和 before/after 约束也会影响 Harmony 执行顺序，最后加载的模组并不必然最后执行补丁。[O2]

2.6 存在“文件名不同，但程序集身份接近”的候选冲突

文件 程序集简单名 程序集版本 Melon 显示名 入口类型
RatColonyOptimizer.dll RatGeneticRenamer 1.0.0.0 Rat Colony Optimizer RatGeneticRenamer.Core
RatGeneticRenamer.dll RatGeneticRenamer 2.6.3.0 Rat Genetic Renamer RatGeneticRenamer.Core

两者哈希不同。日志记录了后者，但没有前者的文件哈希。可提示“程序集简单名和入口类型重复，需确认能否共存”，不能据此断言缺失日志一定由身份冲突引起，也不能将它们简单合并成同一文件。[G5]

管理器的主键不能只用文件名、显示名、程序集简单名或内容 BundleId。需要“本地管理 ID + 版本内容哈希 + 组件身份 + 来源”。多个组件组成同一发行包，还需要独立的 package/component 关系。

2.7 日志开始有 ERROR，不代表本次启动失败

日志开头确实出现 .NET 域初始化失败，随后下载并运行 .NET 6 安装程序，再继续启动 MelonLoader、加载模组，最后到达主菜单相关步骤。[G2、G3]

诊断输出应是“本次启动早期运行库问题，随后恢复”，而不是“游戏无法启动，请重装”。类似地，生成阶段的部分恢复失败、远程 API 未找到游戏、界面对象暂时为空，也不能在缺少后续证据时被自动认定为致命错误。

应建立启动阶段和会话模型：运行库引导 → IL2CPP 互操作准备 → 模组发现 → 内容注册 → 初始化 → 主菜单/游戏内。后续成功证据可以降低早期告警等级，但不能抹去原始记录。

2.8 CFG 扩展名不代表统一语法

本次对 UserData 下五个 CFG 做了只读标准 TOML 解析探测：Loader.cfg、PSMarketRequests.cfg、PSProcurement.cfg 通过；MelonPreferences.cfg 在 L28 中文裸表名处被 Python tomllib 拒绝；PSWallpaper.cfg 在 L4 值处被拒绝。[G6、G7、T1]

这不证明游戏配置损坏，只证明不能套一个标准解析器处理所有 CFG。首版应以保真文本编辑、备份和明确的字段适配器为基础；结构化表单按具体格式逐个开放。不能失败后“自动纠正”整个文件，更不能把多个模组共用的 MelonPreferences.cfg 当成某个模组私有配置覆盖。

3. RimCrow 值得保留什么，不能原样保留什么

3.1 实际技术栈

上传源码是 Python 后端 + pywebview 桌面宿主 + Vue 3 / JavaScript 前端，不是 Electron 或 C# WPF。前端包含 Pinia、Vite、Tailwind、虚拟列表、代码编辑器、国际化和 Markdown 渲染；后端包含 Peewee/SQLite、Pydantic、LiteLLM、keyring、文件/任务基础设施。清单声明 Python >=3.11；这些是依赖范围，不是本环境已经安装完成的版本。[R1–R3]

首版沿用这个栈更有利于保留用户重视的交互与 Agent。可选增加独立 C# 元数据辅助程序，但不建议同时把整个前端、桌面宿主和后端都改写。新平台迁移会把“游戏适配”变成“两个系统一起重建”。

3.2 UI 和交互复用

值得保留多栏工作台、搜索筛选、分组标签、多选批处理、详情面板、虚拟列表、任务进度、日志联动、历史撤销和 AI 操作卡片。优先复用组件与设计规范，而不是原封不动保留所有业务字段。

建议把旧的“未启用/已启用”工作台调整为“模组库/当前配置”，并在列表上区分计划状态、已部署状态和最近一次运行状态。右侧上下文工作台在详情、依赖、诊断、AI 之间切换。底部主按钮采用“检查方案 → 预览更改 → 应用 → 启动”，让用户明确何时修改磁盘。

列表拖动用于分组和展示顺序可以保留，但不能默认宣称改变 Melon 初始化顺序，更不能表示控制 Harmony 的补丁顺序。旧“自动排序”应改成“检查兼容性 / 补齐已确认依赖 / 生成修复方案”。

3.3 游戏核心耦合并不薄

mod_scanner.py 依赖 About.xml 或 DLC 判断；parser_xml.py 解析 RimWorld 元数据与前后顺序；analyzer.py 的严格禁用以 About.xml.disabled 为基础；mgr_profile.py 通过 RimWorld 路径模型和 -savedatafolder 管理环境；载入列表则围绕 ModsConfig.xml。[R4–R7]

这些路径与协议不能直接用于 Probably Stolen。没有证据表明该游戏支持 RimWorld 的存档参数。原有 Steam 工坊应用标识、RimWorld 纹理/翻译/多人兼容规则，也不能顺手保留并启用。

4. RimCrow 的 AI Agent 到底做了什么

4.1 它确实不是普通的单轮聊天框

ai_tools.py 定义七个读取工具：get_log_context、search_mods、get_active_mod_list、get_mod_info、get_mod_rules、get_mod_user_data、get_group_mods。工具有参数模型、结果摘要与结构化错误处理。[R8]

assistant_runtime.py 提供多轮模型/工具循环、流式事件、取消检查、用量处理、轨迹记录和上限；当前常量 ASSISTANT_MAX_LOOPS 为 10。重复调用检测采用函数名与原始参数字符串签名，因此是一定程度的重复阻断，不应理解为已经消除所有语义等价循环。[R9]

内置游戏日志助手已经要求基于日志证据分析、确认准确模组标识、必要时再获取上下文，并约束操作建议。这些设计很值得保留。[R10]

4.2 “读取用户数据”并不是任意读取 UserData 目录

这里的 get_mod_user_data 指管理器中的别名、标签、备注、颜色和分组等用户态信息，不是一个通用的游戏配置/存档文件读取工具。改造时需要新增明确的配置访问能力，不能只改工具说明就当底层已经支持。[R8]

4.3 动作卡片不等于游戏已经修好

游戏助手主要输出 MOD_STATE 和 MOD_RULE。前端 MOD_STATE 分支调用 modStore.changeModsActive；该函数修改列表并进入列表历史事务。MOD_RULE 有确认和规则写入，并可继续触发排序。[R11、R12]

所以准确描述是：读取事实 → 生成解释和结构化建议 → 用户触发管理器已有动作。 在所检查链路中，没有“任意修复 C# 源码、编译并替换 DLL、自动证明游戏已恢复”的万能执行器。列表操作成功也不能代替 Probably Stolen 的文件部署成功和重启后生效验证。

4.4 建议新增的 Agent 闭环

将写操作统一收口为后端 OperationPlan，而不是由模型返回自由路径或让前端直接搬文件：

采集当前环境与本次会话
  → 本地规则提取证据
  → AI 按需调用只读工具
  → 输出诊断与候选计划
  → 后端计算影响范围、校验前置条件
  → 用户批准指定计划
  → 事务部署与结果核验
  → 经授权启动游戏或等待用户下一次启动
  → 对比新日志并给出“已验证 / 部分验证 / 未验证 / 失败”

读取工具建议包括 environment_snapshot、inspect_package、list_deployed_components、read_log_window、get_runtime_status、get_config_view、get_patch_owners、diff_profile。get_patch_owners 可由后期可选探针提供；没有探针时必须说明信息来源和覆盖范围。

计划动作限制为已定义操作，例如停用指定包版本、恢复已知备份、安装库内已核验依赖、修改适配器认可的某个配置键。自动安装系统运行库、替换加载器、删除存档、执行 shell、安装未知 DLL、结束游戏进程不得作为默认隐式动作。

计划必须绑定 plan_id、installation_id、profile_id、base_state_hash、目标文件哈希、证据位置、备份策略、批准范围和过期条件。执行前再核对状态；文件已经被用户或游戏改动时，重新生成计划，不能悄悄覆盖。

游戏更新后不能仅根据“版本字符串没变”继续使用旧兼容结论。文件指纹变化应使缓存失效，提示重新验证。互操作生成文件属于可再生运行时产物，不应作为某个普通模组包的固定资产去覆盖。

5.2 元数据读取与进程边界

适合用 C# 元数据工具读取程序集属性和嵌入资源，而不是在管理器进程中 Assembly.Load 模组 DLL。System.Reflection.Metadata 提供 ECMA-335 元数据读取能力，但官方明确警告相关读取类型并非针对不可信输入设计，恶意或损坏 PE 可能导致崩溃、越界或挂起。[O4]

因此应设置文件大小、资源解压大小、内存、运行时限和输出限制，并为不可信输入设计真正的权限隔离与沙箱边界。单独开子进程不等于安全沙箱。可信度未知时允许只登记哈希和文件，不强行深度解析；生产解析器需要畸形输入和模糊测试。本次使用的审计解析逻辑不是生产级扫描器。

5.3 不把游戏的 net6 依赖扩散到整个管理器

当前游戏样本使用 net6；.NET 6 已于 2024-11-12 结束支持，而核验时 .NET 10 处于 LTS 支持期。[O3]

新写的独立辅助工具可以选择受支持的运行时；游戏内探针仍须服从已验证的 MelonLoader 兼容组合。不要为了统一版本就自动升级用户的加载器，也不要把程序集引用版本误当成最小兼容版本：本快照 JCuratedVisitors 的 MelonLoader 引用版本为 0.8.0.2580，但它在 0.7.3 日志中实际进入了自己的初始化流程，后续自停用理由是旧组件检查。[G3、G5]

5.4 后期可选只读探针

一个体量小、可单独停用的 Melon 模组可输出规范化会话 JSON：已注册模组、初始化事件、运行时 API、Harmony owner/目标方法、主菜单可达和有限心跳。严禁把它变成默认远程命令执行器。

探针失败不能让游戏或管理器无法工作；没有探针仍可用日志和静态元数据。它也不能证明所有玩法都正常，更不能保证捕获先于初始化发生的原生崩溃。

6. 包模型与部署模型

6.1 需要的核心对象

Installation 表示一个真实游戏安装；Package 表示一个发行包；PackageVersion 表示不可变内容版本；Component 表示 DLL 或内容运行时组件；FileEntry 表示部署路径与生命周期；Profile 表示期望组合；Deployment 表示实际提交；GameSession 表示一次运行；Diagnostic 和 ActionPlan 表示证据与计划。

身份字段至少保留 manager_id、来源、SHA-256、文件名、程序集简单名/版本、入口类型、Melon 显示名/版本、内容 BundleId、运行时 API、用户别名。模组显示名称不能做唯一键；未知版本要保存原始字符串，不能把 localfix 等后缀强行截掉或按字典序判“最新版”。

可增设“组件组”将钓鱼物品包、钓鱼人物包、料理扩展呈现为有关联的组合，但关系应注明来自作者清单、明确用户分组还是系统推测。启用依赖闭包时必须把拟变动展示出来；禁用依赖也不能无提示连带删除一串内容。

6.2 三类关系图分离

第一类是包依赖和能力要求，例如 ItemForge API >=19。第二类是文件所有权和覆盖冲突，例如两个版本部署到同一路径。第三类是运行期代码交互，例如相同 Harmony 目标方法或角色商品引用了另一个内容包的 ItemId。

三类图可以在一个界面联动，但不能合成“给模组排个序就都解决”的万能图。规则来源应包含作者清单、嵌入 JSON、已验证兼容库、用户指定或启发式推断，并显示置信度及适用指纹。

7. 部署、回滚和 Profile：稳定性的核心

7.1 首次接管不要破坏手动安装现状

首次选择游戏目录后先扫描、识别、展示不确定项，然后建立当前快照。确认前不移动任何文件。现有文件可以登记为 external / adopted，待用户确认资源归属后再进入包管理，不为了“整理”强行改成每个模组一个子目录。某些二级加载器的搜索方式尚未验证，贸然移动位置可能使内容消失。

7.2 事务状态机

planned → approved → staged → applying → committed
                              └→ rolling_back → rolled_back
                                               └→ recovery_required

执行流程包含：解析并锁定真实安装；检查游戏进程与运行中的加载器；核验部署基线；检查冲突、权限、磁盘空间；生成差异；批准；备份和写持久 journal；逐项替换；校验哈希；提交数据库与部署清单；释放锁。失败后按 journal 恢复，若文件占用或磁盘故障使恢复不完整，明确进入 recovery_required，不显示“操作成功”。

单文件 os.replace 或单目录交换不等于多个 Mods/UserData/UserLibs 路径的一次整体原子事务。文件系统与 SQLite 也不会天然一起提交；需要明确的事务协调、恢复标记和幂等重放。

RimCrow 已有同目录临时文件、fsync、os.replace 的 JSON 写入工具，以及包安装暂存/替换逻辑，这是值得保留的基础，不应说它没有原子写入保护。但它不能直接替代这里的多路径部署协调器。[R13、R14]

7.3 并发、外部修改与运行中操作

每个安装实例只能有一个部署事务。多开管理器、游戏直接从 Steam 启动、用户手动替换 DLL，都必须被考虑。不能只禁用前端按钮：后端应重新检查进程、文件身份和基线哈希。将“游戏运行中排队等待”与“经用户同意关闭游戏”分开，不能为了部署默认强杀。

检测到外部更改时，提供导入更改、保留外部版本或恢复管理版本的差异视图。未知文件一律保留。不能用“清理残留”把不认识的用户数据删掉。

路径校验需要覆盖相对路径逃逸、大小写折叠冲突、Windows 保留名、重解析点/联接、NTFS 备用数据流和超大压缩包。一个安全解析路径检查不能只做字符串前缀判断。普通模组包的目的路径严格限定在其类型允许的目录。

7.4 配置与存档隔离要实事求是

首版 Profile 承诺的是模组版本组合与已支持配置的可重复切换。游戏真实存档路径、配置何时落盘、是否读取启动参数、云存档影响，均需 Windows 实测后再承诺存档隔离。RimCrow 的 -savedatafolder 不能照搬。[R7]

依 app.info 可列出待验证的 Unity 日志候选目录 %USERPROFILE%\AppData\LocalLow\Questing Goose Studio\Probably Stolen\，但压缩包未提供实际 LocalLow 内容，不能把这个推测进一步当成已确认的存档结构。

一个物理游戏根目录只有一套当前部署。两个 Profile 不能通过同一 Mods 目录同时承诺不同组合；没有经过验证的重定向能力时要加互斥约束。不要默认复制整套游戏来伪造隔离，也不要自动关闭 Steam 云同步。

8. AI 和自动化的稳定性、安全性

8.1 自动化等级建议

自动完成读取、增量扫描、已知规则诊断、变化提醒和无破坏性健康检查。对于经用户设置允许的、可回滚且不触及存档的操作，可在明确策略下自动执行。升级加载器、变更模组集合、修改业务配置和关闭游戏，应按风险请求确认；不以用户开启“AI 模式”视为永久授权所有操作。

每次会话按错误指纹聚合，不因同一堆栈重复数千行而数千次请求模型。网络超时、429、提供商不可用时，有限次数重试并说明降级；诊断规则、包管理和启动功能仍可离线工作。预算不足时保留已取得的证据，不伪造已完成全部分析。

8.2 证据数据契约

诊断至少包含 session_id、log_file_id、行号或字节范围、发生阶段、原始片段哈希、相关组件、规则来源、结论强度、后续恢复证据和可能操作。日志轮转/截断后不要让同一个行号指向不同内容。

归因分“已观察”“合理推测”“需要复现”。举例：旧组件自停用是明确日志事实；哪个旧 DLL 应移除需要身份映射；是否会破坏既有存档需要迁移证据。AI 不得把这三步压成一个没有依据的“已修复”。

8.3 凭据、隐私与提示注入

保留 keyring 和脱敏设计，禁止把模型 API Key 写入导出配置、日志或诊断包。RimCrow 已有 keyring 写入失败时拒绝继续的分支，不能为了“兜底”改成静默明文保存。[R15]

默认只发送任务需要的日志窗口和结构化元数据。完整存档、全目录、私人绝对路径和聊天/令牌信息不自动上传。显示发送范围与提供商。规则库和第三方文档同样是数据，不得提升模型权限。

工具权限要在后端执行时校验，而不只是从模型看到的工具列表里隐藏。批准的是一个具体、有版本与前置条件的计划，而不是一句模糊的“允许 AI 帮我修复”。

8.4 RimCrow 浏览器模式应先整改

静态检查发现 BrowserAppServer 监听 127.0.0.1；get_available_methods 枚举大部分公开可调用方法；/api/call/ 分支在所检查代码中直接分派调用，未校验会话或 Origin；公共响应头设置 Access-Control-Allow-Origin: *。静态目录边界还使用字符串 startswith 检查。[R16]

这些组合构成需要优先审查的本地桥接暴露风险，不能把“只监听 localhost”当充分防护。本次没有做浏览器攻击复现，也不把它宣称为经过利用验证的漏洞。

建议首版关闭浏览器模式，仅提供受控桌面入口；要开放时再加入显式接口白名单、强随机会话凭证、Host/Origin 校验、请求大小上限、路径/操作权限和正常化路径边界验证。外部网页内容与管理器权限桥接分离；桌面 WebView 也不是因此免于安全检查。

10. 功能优先级与实施阶段

阶段 A：验证原型

目标是把 45 个 DLL 全部登记，识别无 MelonInfo 的内容包，展示真实日志状态，并在临时测试目录验证部署恢复。同步完成旧代码依赖与窗口启动复现，以及实际 Windows 的路径/配置/文件占用验证。此阶段不接自动写入 AI，也不以替换 logo 作为主要成果。

阶段 B：可靠 MVP

14. 最终建议

选择“独立分支 + 选择性复用 + 游戏核心替换”。

第一优先级不是 AI 模型更聪明，而是事实识别准确：能区分代码模组与内容包，知道哪些文件属于谁，知道日志属于哪次运行，知道修改能不能撤回。第二优先级是把这些能力组织成可重复的部署与诊断闭环。第三优先级才是让 AI 更主动地运用这些确定性能力。
